# 190. 失敗に「何の途中か」を添える・縦の断面を見る道具

2026-10-18。自己改善（失敗を読んで技や手を直す）は、失敗のフィードバックの質で決まる。新しいワールド（world16）の約 3 時間で、
直せなかった失敗のほとんどが、次の 2 つで読めなかった。

## 1. 失敗に、何をしている途中だったかを添える

### 起きたこと
mine_2 の `dig the mine` が「147,16,139 へ経路が決まらない」で 3 回止まった。実際は、掘る前の「暗いセルを明るくする」手が出した
失敗だったが、記録には「`dig the mine` が失敗した」としか出ない。LLM にも調べる側にも、掘る手の失敗に見えた。原因は地形を
プローブして初めて分かった（設計書 187 §3.3）。

### 決めたこと
- プリミティブは、途中の段階を `bot.actionPhase` に書く（歩く手はすでに `walking toward …` を書いていた。止めた理由には、すでに
  `(while …; moved Nm)` で添えていた）。
- 投げた失敗にも添える: `runner.mjs` が、`failed: <元の文> (while <phase>)` にする。**元の文は先頭のまま**にする（`refusals.mjs` と
  `same_cause.py` が先頭を見る。`reason_key` は先頭 200 字で、末尾の phase は同じ理由の判定に入らない）。
- 止められた（中断・反射・見張り）ときは、止めた側の文のまま（二重にしない）。
- `dig_mine` の段階: 掘ったセルを明るくする / 階段を下りる / セルの横に立つ / セルを掘る。暗いセルへ歩く間は、そのセルの座標。

### まだ書いていないプリミティブ
`make_mine` は `dig_mine` を呼ぶので、内側の段階がそのまま出る。ほかの複数段のプリミティブ（建築、畑、かまど、`reach_land`）は、
必要になったときに `bot.actionPhase` を書けば同じ形で出る（足したら、runner のテストはそのまま通る）。

## 2. 縦の断面 `cross_section`

### 起きたこと
周囲の情報は真上から見た高さだけで、湖の岸の高さ（3〜4 ブロック上）、岩の厚み、頭の上や足元に何があるかは横から見ないと分からない。
水の中で岸の高さが分からず 17 分動けなかった。

### 決めたこと
- 調べものの道具（すぐ返る、世界を変えない）。`direction`（north / south / east / west。省くと見ている向き）、`length`（12、最大 24）、
  `down`（12、最大 24）、`up`（4、最大 12）、`x` `z`（起点。自分から 32 以内）。LLM に渡す定義は `direction` だけ（プロンプトの大きさ。
  `test_context_budget.py`）。`x` `z` `length` `down` `up` は、技（`t.cross_section`）から使える。
- 出力: 行が高さ、列が距離の文字の格子（`.` 空気、`~` 水、`S` 石、`D` 土、`g` 砂利、`s` 砂、`T` 原木、`l` 葉、`O` 鉱石、`L` 溶岩、`@` 自分、
  `?` 読み込まれていない）、凡例、`summary`（地面の高さ・水面と深さ・岸が水面より何ブロック高いか・段差）。
- **見えないところは言わない**（視聴者に違和感がある。「水に当たったら壁で塞ぐ」と同じ考え）: 固いブロックは、空気・水・溶岩・
  通り抜けられる物に 1 面でも触れていれば名前を出し、岩の中は `#`。岩に埋まった鉄鉱石や砂利は出ない。洞窟の壁に露出した鉱石は出る。
- 表面の言葉は、各列を上から見て最初の固い所か水面で決める。上端が固い（岩の中にいる）ときは `solid all the way up`。
- 配線: ブリッジ `tools.mjs`（`QUERY_TOOLS`）、Python `tool_catalog.py`、`abilities.yaml`（experiment と cross_water）。
  道具の定義が 1 つ増えるので、配信を再起動したときにプロンプトのキャッシュが 1 回外れる（設計書 177）。

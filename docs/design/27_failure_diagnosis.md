# 進まないときは原因を分析してから、必要なら目標を変える

作成: 2026-09-26。13（目標の階層）と 26（小目標は Jev が選ぶ）の、失敗の後の目標の決定を変える。

## 1. 目的

ユーザー（2026-09-26）: 「続いて進まなければ、Gemini に原因分析をしてから、必要であれば目標の再設定をするようにしてほしい」

きっかけ（2026-09-25 のログ、00:08〜00:12）:
- `have(food, 2)` が 8 ステップ進まない → Gemini が `have(food, 1)` → また進まない → また `have(food, 1)`。約 1 分ごとに Gemini（medium、画像つき）を呼び、同じことを繰り返した
- 行動は東と南の探索を行ったり来たり（Jev の確信度 0.1〜0.4）。満腹度 0 なのに `pick up rotten_flesh` を選ばず、前に見た豚（`go to pig seen at …`、家から約 300m）にも行かなかった
- Gemini には「stalled (no progress in 8 steps)」と今の状態しか渡っていなかった。何を選んで何が起きたか（行動の記録、出ていた候補）は見えていない。だから原因が分からず、同じ小目標を少し小さくして選び直すしかなかった

## 2. 形

小目標が行き詰まった（stuck: 行動が 3 回続けて失敗）か進まなかった（stalled: 8 ステップ残りが減らない）ときは、今も Gemini の目標の決定（`goal_after_failure`、画面の画像つき）を呼んでいる。この呼び出しを次のように変える。呼び出しの回数は増やさない。「考え直す」（reconsidered: 画面の見直しや、視聴者の頼みを今やる）は失敗ではないので、今までどおり分析しない。

```
失敗で終わった小目標
  → Gemini（1 回）: 
      1. 分析（diagnosis）: なぜ進まなかったか。記録と状態の、どの事実からそう言えるか
      2. 対処（remedy）:
         - retry: 同じ小目標をやり直す。やり方の助言（advice）を必ず付ける（選択器が読む）
         - change: 別の小目標にする（今までの目標の決定。中目標リストの編集、メモも）
```

- 出力の JSON は `diagnosis` を最初に置く（スキーマの順番）。先に原因を書いてから対処を決めさせる。分析と決定を別の呼び出しにしないのは、費用を増やさないため（入力は同じもの。分けると入力を 2 回払う）
- `retry` か `change` かは Gemini が決める（「必要であれば再設定」）。コードが決めるのは次の上限だけ:
  - 失敗の後に同じ小目標（述語と品目が同じ。`have(food, 2)` と `have(food, 1)` は同じ）を選ぶなら、`advice` が必須（助言なしのやり直しは同じ失敗を繰り返すだけ）
  - 同じ小目標が続けて 2 回失敗したら、3 回目は選べない（`change` のみ）。理由を付けて差し戻す（今の作り直しの仕組み）
- 助言（advice）: 選択器への 1〜2 文（英語。Jev の状態は英語）。出ている候補に即して書く（例: "Pick up the rotten_flesh and eat it; stop exploring east and south alternately, keep going west"）。今の小目標の間だけ有効
  - 候補モード: Jev の状態に `advice` として入る
  - 道具モード: 道具の選択の「今していること」に出る
- 分析（diagnosis）: 日本語の 1〜2 文。ログに出し、「今していること」に「前の小目標がうまくいかなかった理由」として出す。実況が目標の変わり目で読むので、配信者が理由を話せる（例:「このあたりは雪で動物がいない。前に見た豚は遠い」）

## 3. 分析に渡すもの

今の「今していること」（持ち物、体、覚えている場所、直近の行動 5 件）に加えて、失敗で終わったときだけ:

- **失敗した小目標の行動の記録**: その小目標の間の各ステップ（最大 12 件、古い順）: 選んだ行動、確信度、結果（成功・失敗と一言）。候補モードでは選択器（Jev）が選んだもの、道具モードでは Gemini が呼んだ道具
- **最後に出ていた候補**: 候補の id と、距離・前に行ったか・何分前に見たか（候補の説明に入っているもの）。最大 12 件
- **進み具合**: ブリッジの `lines` と `blocked`（今までどおり）
- 画面の画像（今までどおり、撮れるとき）

記録は `AdvancePlay` が小目標ごとに持つ（小目標が変わると空にする）。ドメインの `Activity` には入れない（実況と返答には要らない）。

## 4. 変えないこと

- 失敗の判定（stuck は 3 回続けて失敗、stalled は 8 ステップ残りが減らない）
- 達成・ステップの上限・時間帯の変化で終わったときは今までどおり（Jev が手順から選ぶ、26）。分析はしない
- 完了の判定はブリッジだけ

## 5. 実装

- domain: `Goal.advice`、`Goal.diagnosis`（その小目標を決めたときの、前の失敗の分析）
- `goal_vocabulary`: `goal_schema(..., after_failure=True)` で `diagnosis`（必須、先頭）と `advice` を足す。`GoalDecision.diagnosis`、`advice`
- `AdvancePlay`: 小目標ごとの行動の記録（`deque`、12）。失敗のときは記録と最後の候補をプロンプトへ。上限（助言なしのやり直し、3 回目）を確かめて差し戻す
- `GamePromptTemplateBuilder`: 失敗のときだけ「## うまくいかなかった小目標の記録」の節。システム指示に分析と対処の書き方
- 選択器の状態に `advice`、「今していること」に分析と助言
- 設定はなし（失敗の後の呼び出しは今もある。出力が 100 トークンほど増えるだけ）

## 6. 検証

- 単体テスト: 失敗のときだけスキーマに diagnosis が入る、助言なしのやり直しは差し戻す、3 回目は選べない、`have(food, 2)` と `have(food, 1)` を同じと数える、記録がプロンプトに入る、助言が選択器の状態に入る、分析が「今していること」に出る
- 実機: 食べ物探しのような詰まり方で、分析が記録に即しているか（`/debug/gemini` で出力を見る）。同じ失敗の繰り返しが減るか（ログの `stalled` の連続）

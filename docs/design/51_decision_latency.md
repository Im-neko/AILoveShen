# 51. 判断のサイクルの遅さ

作成: 2026-09-29。19（道具と考える深さ）、21（道具での操作）、36（ローカルの LLM）、43（行動の途中の一言）に関係する。

ユーザー:「判断のサイクルが遅い。時間がかかっている箇所を特定してほしい。単純に LLM が遅いなら仕方ない」。

## 1. 測ったこと（`data/logs/ailoveshen-dev.log`、9/28 22:34 からの 43 分、104 手）

1 手 24.6 秒。内訳（LLM の時間は重なりがあるので合計は目安）:

| 用途 | 回数 | 平均 | 全体 |
|---|---|---|---|
| 道具の選択（`tool` / `tool_after_failure`） | 103 | 約 8 秒 | 33% |
| 目標の決定（`goal` / `goal_after_failure`） | 78 | 9〜11 秒 | 32% |
| 実況（`commentary`） | 33 | 9 秒 | 12% |
| ゲームの行動そのもの | 104 | 3.9 秒 | 16% |
| Jev | 31 | 0.4 秒 | 0.5% |

ブリッジ側は遅くない。LLM の呼び出しが約 80%。

呼び出しの時間は、入力トークン・出力トークンとの回帰（3,619 回、R²=0.97）で「固定 1.5 秒 + 読み込み約 3,100 トークン/秒 + 出力約 71 トークン/秒」。つまり**入力の大きさでほぼ決まる**。

## 2. 原因

1. **道具の定義が入力の 7 割**: 道具の選択は約 1.6 万トークンで、道具 35 個の定義が 11,337 トークン、状態の本文が 4,295 トークン。行動の道具 26 個すべてに `intent` と `watch`（説明、`items` の 2 項目、`on_yes` の enum）が付き、1 つあたり約 200 トークン。
2. **プレフィックスキャッシュが本番で一度も効いていない**: `cached=0` が 3,617 行、入力 1.2 万トークン超の 1,313 回のうち 2.5 秒未満は 0 回。FreeToken（0.1.3、RTX 5070 Ti）に直接送って確かめた（`/v1/cache/status`、`/v1/stats`）:
   - 同じプロンプトの 2 回目: 1.8 秒（キャッシュが効く）
   - 末尾に 1 行足す: 6.2 秒 / 先頭に 1 文字足す: 6.7 秒（全部読み直す）
   - モデルは `hybrid_linear`（Gated DeltaNet 混在）の MoE で、サーバーは再帰状態の保持枠（mamba slots）を 24 個持つ（1 枠 64 MB、`/v1/cache/rebuild` で 16〜182）。**部分一致の先頭を再利用する仕組みは見えず、完全一致のときだけ効く**（推測を含む: サーバーの実装は確認していない）。
   - 設計書 36 §4 と WORKLOG の「先頭のキャッシュを複数持てる」は誤読だった。`llm_probe` の A→B→A は完全一致同士の比較で、部分一致を見ていない。設計書 26 §4（キャッシュに向くプロンプト）は、この構成では効かない。プロンプトの並べ替えでは解決しない。
3. **失敗のたびに 1 手（約 8 秒）**: 道具の選択の 76% が `tool_after_failure`。失敗は 3,465 手中 926（27%）。多いもの: `No path` 約 100、家・建物の一部で断られた `dig` / `place` 約 110、`pickup` 拾う物なし 22、反射が動いていて断られた 58 以上、手つかずの作物 16。
4. **同じ失敗を繰り返して、同じような実況を続ける**: 9/29 12:26〜12:28 に、夜にゾンビが近い中で `go_home` を 3 回、同じ intent で呼び、その意図がそのまま読み上げられた。

## 3. 直したこと

1. **道具の定義を小さくした**（11,337 → 6,839 トークン、1 呼び出しあたり約 1.4 秒）: `watch` は「`<on_yes>: <質問>` の文字列」の配列にし（`tool_catalog._WATCH`、`parse_tool_call`）、書き方と `intent` の例は道具の選択のプロンプトの「決まり」に 1 回だけ書いた。`watch` の形を変えたので、以前のオブジェクトの形は受け付けない（リリース前）。
2. **失敗を LLM に戻す前に防ぐ**:
   - 反射が動いている間は道具も候補も断られる。`AdvancePlayUseCase._wait_out_reflex` が、ステップの最初に `GET /state` の `reflex` を見て、終わるまで待つ（モデルに選ばせない）
   - `GET /state` に `pickup_ready`（`pickup` が拾える落とし物があるか。`tools.mjs` の `DROP_RADIUS` と同じ範囲）。なければ `pickup` を出さない
   - 「目の前のブロック」（`around.mjs`）から、断られる場所（今の家、建物、建てている家。`protectedReason`）を外した。近い順の最初が家の壁の原木で、座標をそのまま `dig` に使って断られていた
   - 見送り: 引数の欠け（`x, y and z must be numbers`）はモデルに聞き直すしかなく、検査しても時間は減らない。`sleep` の昼の断りはサーバー側の判断なので、ブリッジでは見ていない。`find_blocks` の結果に保護の印は付けていない
3. **実況を状況が変わったときだけにした**（`LiveNarration`）: 黙っている間隔が `live_interval_seconds` を超え、かつ前の一言から持ち物・位置（10m）・体力（3 以上減った）・時間帯・家の出入りのどれかが変わっていたときだけ話す。変わらなければ何秒でも黙る。`Activity.failing`（今の小目標で続けて失敗した行動の数）が 2 以上の間は話さない。`live_interval_seconds` 10 → 30、`max_silence_seconds` 60 → 180。小目標が変わったときの実況（`Narrator`）は今までどおり。
4. **行き詰まったら考えて別の方法を選ぶ**: 小目標で続けて 2 回失敗すると、道具の選択は `purpose=tool_stuck`（考える。`gemini.thinking_levels`、`llm.local.thinking_purposes`）になり、プロンプトに「行き詰まっている」の節（`TOOL_STUCK_SECTION`）が入る: 失敗の理由を読む、同じ道具・同じ引数（近い座標）を繰り返さない、原因ごとの別の方法、分からなければ検索の道具で調べる。

## 4. FreeToken について（調べただけ。設定は変えていない）

- `/v1/stats`: サーバー側の読み込みは約 5,700 トークン/秒、最初のトークンまでの平均 3.6 秒、記録された 2,578 リクエスト。こちらから測った 3,100 トークン/秒との差は、待ち時間とネットワーク（同時 2 本のとき互いに遅くなる疑い。直接は測っていない）
- 部分一致のキャッシュが欲しければ FreeToken 側の実装か設定の話で、クライアントからは変えられない。`/v1/cache/rebuild`（`num_mamba_slots` など）は配信中に呼ばない（`mode: if_idle`、管理用）

## 6. 追加（2026-09-29 午後）: 断られた手の台帳、動かないとき、5 分の確認

配信で 12:55〜12:57、掘れない原木（家の壁、建物）を `search_memory` と `find_blocks` から選んで 2 回断られ、同じ `goto` を 3 回呼び、持っていない原木から板材を作ろうとした。Jev の候補には遠い木しかなく、断られた手は次に活かされず、失敗のたびに Jev が外れて LLM の 7 秒を使った。

- **使えない場所を情報源で外す**: 家・建物・建てている家のブロックは、記憶（`remember` の前）、`find_blocks`、「目の前のブロック」に出さない
- **台帳**（`minecraft-bridge/src/refusals.mjs`、`state.refusals`）: 同じ場所への同じ手（動作の種類 + 座標）が、断られた・着けなかった（`No path`、経路探しの時間切れ、掘るものがない、実っていない、ふさがっている、家・建物の一部）なら **1 回で** 載せ、5 分（`NO_PATH_MS`）まで、候補（`withheld` に理由）・`find_blocks`・道具の呼び出し（実行せず、前の理由と「別の場所か別の手を」を返す）から外す。反射・ダメージ・見張りの中断、遠すぎる、持っていないは載せない（一時的）。掘れなかった場所へ歩くのは妨げない（動作の種類ごと）。`GET /state` の `refusals`（最大 8 件、理由と何分前か）が道具のプロンプトの「しばらく使えない手」になる。1 回で載せる理由: ブリッジが弾く理由（保護、経路、実り）は世界が変わるまで変わらず、期限で戻すので、2 回目を待つと 1 手（LLM の 7 秒）が無駄になるだけ
- **断りの後も Jev が選ぶ**: 断られた（`refused`）ときは、失敗として LLM に回さない（台帳で外れたので、残った候補から Jev が 0.2 秒で選ぶ。迷えば LLM）。実行して失敗したとき（`failed`）は今までどおり LLM
- **10 秒動かなければ選び直させる**（`Stagnation`、`minecraft.agent.stagnation_seconds`）: 位置・持ち物・体力・満腹度・時間帯・小目標の進み具合が 10 秒変わらず、その間に 2 手以上した（待つ・寝るは数えない）とき、Jev に任せず（`_jev_step` を飛ばす）`purpose=tool_stuck` で、その間の手と結果を「行き詰まっている」の節に見せる。失敗が続かない空回り（成功して何も変わらない）にも効く。一言も黙る（`Activity.stagnant_seconds`）
- **5 分の確認**（`StuckCheck`、`minecraft.agent.stuck_check_quiet_minutes`）: 小目標の進み具合（残りと進捗の行）が 5 分変わらなければ、6 手ごとを待たずに行動の記録を Jev に渡して確かめる（`minutes_without_progress` つき）。行き詰まりと確かに答えたら（0.75 以上）従来どおり Gemini が考え直す。答えたあとも変わらなければ、また 5 分後
- **考える長さの上限**（`llm.local.thinking_max_tokens: {tool_stuck: 8000}`（最初は 3000 にしたが、上限なしの思考は 2,920 / 6,494 / 11,408 トークンで、3000 は 2 回とも 43 秒考えて切れ、思考を捨てて無駄になった。8000 なら約 2 分が最悪））: 思考で上限に届いたら、思考なしで聞き直す（思考なしの用途・上限のない用途は従来どおり）。12:57 の `tool_stuck` は思考だけで 2,920 トークン、57 秒、その次は数分止まった

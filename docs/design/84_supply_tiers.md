# 84 ストックの段階（松明と食べ物を、生活インフラの整い方で変える）

2026-10-02、状態: 実装済み、**序盤の段階だけ**ベンチマークで確かめる（§6）。後ろの段階は実機で未確認。

## 1. きっかけ

ベンチマークの `pickaxe` で、始まりの **食料 16 個のストック**（`have(food, 16)`）に 3〜6 分かかっていた（設計書 83 §10: 826 秒のうち 126 + 59 + 164 秒など）。ストックは user の 2026-10-01 の頼み（「食料や松明はその時必要なぶんじゃなくて、ある程度手持ちにストックするようにしてほしい」）で、固定値（食料 8 → 16、松明 16 → 32）だった。user の答え: 「理想は生活インフラの整い方次第でストックする量を増やしていきたい。序盤は 16 本もあるが、本格的に採掘をするようになったら 1 スタックは最低ほしい」。

## 2. 段階表（`config/default.yaml` の `minecraft.supplies`）

一覧は前から順に、**着いている段階のうち一番後ろ**が今の段階。段階に着く条件は、`after` の定石の段がすべて済んでいる（`playbook_done`）か、`or_mine` で鉱山が設計済み（ブリッジの `mines`）。

| 段階 | 着く条件 | 松明（下限 / 手に持つ / 合計） | 食べ物 |
|---|---|---|---|
| `early` | いつも | 8 / 16 / 16 | 4 / 8 / 8 |
| `settled` | 定石 `food`（畑の最初の収穫）が済み | 16 / 16 / 32 | 16 / 16 / 32 |
| `mining` | 定石 `lumber` が済み（`iron` が今の段）、または鉱山が設計済み | 32 / 64 / 128 | 32 / 32 / 64 |

- `low`: 手持ちと家のチェストの**合計**がこれを下回ったら、集める小目標 `have(item, carry)` を出す
- `carry`: 手に持つ量（集める小目標の目標。出かける前にチェストから取る量）
- `stock`: 手持ちとチェストの合計で持ちたい量。`carry` を超えるぶんは家のチェストの備蓄
- 数の関係は `1 <= low <= carry <= stock`（`Supply` が確かめる）。名前の重複は `create_supply_tiers` が断る

定石が空（ベンチマーク）なら、鉱山がなければいつも `early`。

## 3. 備蓄の考え方（user の確認: チェストを含めて数え、出かける前に取り出す）

ブリッジの `supplies`（`/observe`）に、`food_stored` / `torch_stored`（家のチェストを**最後に開けたときの中身**。古いことがある）と `mines`（設計した鉱山の数）を足した。家にチェストがなければ手持ちだけで数える。

- 合計が `low` を下回る → 集める（`have(item, carry)`）。ソルバーは先にチェストから取り出すので、チェストに備蓄があれば取り出してから作る（`forced` は今までどおり: 材料が手元にある、暗くて 0 本、食べ物が合計 0）
- 合計が足りている:
  - **出かける前に取る**: 昼、家の中、チェストにあり、手持ちが `carry` の半分以下 → `have(item, min(carry, 手持ち + チェスト))`（強制しない）
  - **備蓄を貯める**: 昼、手持ちが `carry` に届いていて、チェストが `stock - carry` に届かない → `stored(item, stock - carry)`（強制しない）

`have` は手持ちだけ、`stored` は家のチェストだけを数える（両方を足す条件はない）ので、1 つの条件にまとめず、順に出す 2 つの小目標にした（`together` で束ねると、`stored` の預け入れが手に持つぶんまで預けて、`have` の目標と取り合う恐れがある。実機で確かめていないので避けた）。備蓄を貯める小目標は Jev が選ぶ（強制しない）ので、必ず貯まるわけではない。

死ぬと持ち物は落ちて 5 分で消える（設計書 66・76）。採掘の段階で 64 本・32 個を手に持つぶんは失うおそれがあり、備蓄はチェストに置くことで守る、という分担。

## 4. 変えなかったもの

- `TORCH_LOW`（4 本。暗い所で置けない「もう危ない」本数）は段階によらない: 理由の書き方、`needs()`、ブリッジの `craft torch` 提案

- 空腹のときの食べ物集め（`have(food, 4)`）

## 5. 見つけたこと（ベンチマークの記録から）

食料のストックが `pickaxe` の始まりに 3〜6 分を使っていた。食料 0 個で強制されることと、序盤は畑がなく、16 個は牛・羊を追う遠出になることが原因。序盤の食べ物を 8 個（下限 4）にした。ベンチマークの `food` 課題の条件は `have(food, 8)`で、序盤の段階の目標と同じ数になる。生存の小目標と課題の小目標が重なるので、`food` の秒は「生存の routine」込みの値になる（読み違えないこと）。

## 7. 序盤の段階を測った結果（サイクル 2、2026-10-03、バッチ `20261002T143025Z`）

前のバッチ（`20261002T131703Z`、食べ物 16）と同じ課題・同じ回数。仕組みの数字は、生存の小目標 `have(food, N)` に使った秒（`goal_ends` の `survival`、重複行は除く）。

| 実行 | 食べ物 16（前） | 食べ物 8（後） |
|---|---|---|
| `pickaxe` の 1 / 2 / 3 回目 | 348 / 161 / 176 秒（62 歩） | 314 / 72 / 185 秒（50 歩） |
| 成功 | `food` 3/3、`pickaxe` 3/3 | `food` 1/3、`pickaxe` 3/3 |
| `pickaxe` の成功までの秒 | 482 / 629 / 826 | 215 / 497 / 591 |

読み方:
- **「食べ物を 16 → 8 にすれば、始まりの 3〜6 分が消える」は確かめられなかった。** `pickaxe` で生存の食べ物に使った合計は 685 → 571 秒（約 17% 減）で、3 回では揺れの範囲。1 回あたり 72〜314 秒が、まだ食べ物集めに使われている
- 原因は個数ではなく、**食べ物が 0 個だと強制される**こと（`forced`: Jev に聞かず、課題の前に必ず食べ物探しに出る）と、食べ物を**探す**手間（個数を半分にしても、探しに出る手間は変わらない）。最悪の回は 31 歩（探索の繰り返し）
- 成功の数は `food` 3/3 → 1/3、`pickaxe` 3/3 → 3/3。`food` の 2 回は食べ物が見つからず探索を繰り返した／水に落ちて `goto` が 8 回失敗した回で、段階表との関係は示せない。同じ版でも `food` は 3 バッチで 2/3、3/3、1/3 と揺れた。**成功の数では、この大きさの変更は判定できない**
- `pickaxe` の最短は 215 秒（これまでの最短は 299 秒）だが、n=3 では運と区別できない

次の候補: 序盤の食べ物を、**空腹が近づくまで強制しない**（`forced` を、食べ物が 0 個で、かつ満腹度が下がってきたときだけにする。そうでなければ Jev が中目標と比べて選ぶ）。user の「食料は切らさず持つ」を、空腹より先の「必要になる前」に保つ範囲で、課題を邪魔しない形にする案。user の判断を待つ。

## 8. 暗くて松明がないとき引き返して作る本数（2026-10-03）

洞窟で松明を置かない、との指摘。引き返して作る仕組みは動いていたが、暗くて 0 本のときの目標が 4 本で（`torch_options`）、約 10 m 間隔の `trail` で 40 m 歩くと尽き、また止まって 4 本だけ作る繰り返しになっていた（07:51 に作って 08:04 に尽きた）。user の答え: 本数は `stock`。暗くて 0 本で引き返すときは段階の `stock` まで（材料があればその分、家のチェストにあればそのぶんが上限）。暗くないときの補充は従来の `carry`。材料（石炭・棒）が足りずに作れない場合は、これまでどおり solver が集める。採掘の段階（`stock` 128）では石炭 32 個と棒が要る。教えの想起には `dark_here` と `torches_carried` を渡す（設計書 35 §4）。

## 9. 食べ物は満腹度で数える（2026-10-03）

user の指摘: 食料の必要量の見積もりが甘い。`have(food, n)` は個数だけで、じゃがいも 8 個（満腹度 8）も焼いた肉 8 個（64）も同じ「8 個」だった。回復量は minecraft-data の `foodsByName[x].foodPoints`（`find_foods` / `item_info` で LLM も見られる）にある。満タンは 20、歩くと 40〜70 m で 1 減る。

- **述語は個数のまま**（案 (a)）。`have(food, n)` はソルバー（`take N from the chest`、狩り、畑）も判定も個数で動く。満腹度を述語にする案 (b)（`fed(points)`）は、述語の語彙・スキーマ・プロンプト・ベンチ設定・`plan_lint` まで広がるうえ、ストックの小目標を出すかどうかは Python が決めるので判定に満腹度は要らない
- ブリッジの `supplies` に `food_points`（手持ちの満腹度）と `food_points_stored`（家のチェスト、最後に開けたとき）を足した（`cooking.mjs` `foodPointsIn`）。個数 `food` / `food_stored` はそのまま。**生の肉は、かまどが分かっている（`knownFurnace`）ときだけ焼いた値で数える**。なければ生の値（かまどがないのに焼ける前提で見積もらない: 2026-10-01 の 18 食中 16 食が生だったのは、かまどがなかったから）。腐った肉などは数えない
- 段階表の食べ物は満腹度（`config/default.yaml`、**値は推測**）: `early` 12 / 24 / 24（以前の 4 / 8 / 8 個を生の豚肉 3 点で換算。user が決めた序盤の大きさを変えない）、`settled` 40 / 80 / 160（16 / 16 / 32 個を 5 点で）、`mining` 100 / 160 / 320（32 / 32 / 64 個）。松明は本数のまま
- Python は足りない満腹度を `FOOD_ITEM_POINTS`（5 点: 生 3 と焼いた 8 の間、パン）で割って個数にし、`have(food, 手持ちの個数 + その個数)` を出す。見積もりが外れても、次の境目で満腹度がまだ足りなければ、また出る。チェストから取る小目標（`take`）と貯める小目標（`stored`）も同じ換算（`_reserve_options` の `items_for`）
- 空腹の食べ物集め（`FOOD_WHEN_HUNGRY` の `have(food, 4)`）は `hungry_option`: 満タン（20）と段階の `low` の大きいほうに届くぶん（手持ちの個数に足す）
- **食べ方**（`candidates.mjs` `forNeeds`、`primitives.mjs` `eat`）: 食べる物は、捨てる点数（`points − (20 − 満腹度)`）が少ないものから、同じなら大きいものから。捨てる点数が `EAT_WASTE_OK`（3）を超える物は、飢えそう（満腹度 ≤ 6）か回復のため（次の項）のほかは出さない（満腹度 19 に焼いた肉を食べて 7 点捨てない）。1 回の `eat` は、満腹度 20 になるまで同じ物を続けて食べる（次の 1 個が `EAT_WASTE_OK` を超えて捨てるならやめる。1 手に 1 個だった）
- **体力が減っているとき**: 回復は満腹度 18 以上のときだけ。体力が `HEAL_BELOW`（16）以下で満腹度が 18 未満なら（`healing.mjs` `needsFoodToHeal`）、捨てても満腹度 18 になるまで食べる（`healTo`）。敵がいなければ `urgent`（Jev に聞かない。体力 8 以下は敵がいても、これまでどおり）。かまどがなければ生肉でも食べる。`needs()` に `health 12/20 and food 15/20: it heals only while food is 18 or more` を足した（数だけ。「hunger」とは書かない: Python が空腹と読む）
- ベンチマーク（設計書 83）の `food` 課題は `have(food, 8)` のまま（版どうしを比べられるように）。ストックの小目標は定石を空にした序盤の段階で、段階表の単位だけが変わる（序盤は 24 点 = 生肉 8 個で以前と同じ）
- テスト: `test/cooking.test.mjs`（満腹度の合計、食べる物の選び方、体力が減っているとき、続けて食べる）、`test_supply_tiers.py`（満腹度の換算、同じ個数でも足りる・足りない、チェスト）。**実機では未確認**（再起動後、`logs` の `eat` と `have(food)` の目標の個数を見る）。決めていない: 動物を狩る・畑を待つ・チェストから出すのどれが得かを満腹度の費用で比べること（`find_foods` の `now` が材料を出す: 設計書 47 追記）

## 2. 記録するもの

### 2.1 小目標の終わり（`logs/goal_ends/watch-*.jsonl`）

`AdvancePlayUseCase._end_goal` が、`session.set_goal` が歩みの数えを消す前に、終わる小目標を 1 件書く（`goal_ends.py` `goal_end_entry`、`goal_end_recorder`、設定 `minecraft.goal_end_record_dir`）。書けない・作れないときも、プレイは止めない（警告だけ）。

| 欄 | 内容 |
|---|---|
| `goal` / `predicate` / `kind` | 目標の文 / 述語 / 数を無視した種類（`have(food, 16)` と `have(food, 4)` は `have(food)`） |
| `together` | 束のほかの条件の数 |
| `survival` / `objective` / `playbook` / `viewer` | 生存のためか / 仕えた大目標の題 / 定石の段の名前 / 視聴者の頼みか |
| `category` | 後述 |
| `reason` | `goal_end_reason` の文そのまま |
| `resumed` | 再起動で引き継いだ小目標か（`PlaySession.goal_resumed_at`）。そうなら `started_at` は続きから追い始めた時刻で、止まっていた間は秒数に数えない（歩数・死亡は引き継いだ数え） |
| `started_at` / `ended_at` / `seconds` | 小目標を決めた時刻 / 終わった時刻 / その差（Gemini や Jev の決定の待ちを含む） |
| `phase_start` / `phase_end` | 始まりと終わりの時間帯 |
| `steps` / `consecutive_failures` / `stalled_steps` | 行動の数 / 続けて失敗した数 / 進まなかった数 |
| `least_remaining` / `remaining_end` | 一番減ったときの残り / 終わりの残り |
| `deaths` | 小目標の間に増えた死亡の数（ブリッジの数。分からなければ null） |

### 2.2 終わり方の分類（`end_category`）

`goal_end_reason` の文の最初の節で分ける（後ろに足される「大目標が進まない」は小目標自身の終わりではない）。

- `met`: 達成
- `failed`: 行き詰まった（`is stuck`）、進まなかった（`stalled`）、ステップの予算を使い切った（`ran for N steps`）、大目標が進まない印だけで終わった
- `died`: 死んでリスポーンした
- `cut`: 成否と関係なく切った（時間帯の変化、夜が明けた、考え直し `is reconsidered`、仕えた大目標が終わった）

成功率は `met / (met + failed + died)`。`cut` は成功でも失敗でもないので、分母に入れず別に数える（夕方に切れる分を失敗に数えると、日の長さで成績が動く）。`reconsidered` は理由の文に stuck などが入っても `cut`。

### 2.3 実行の条件（`logs/runs/watch-*.jsonl`）

`GameService.play` の始まりに 1 件（`infrastructure/run_info.py` `collect_run_info`、設定 `minecraft.run_record_dir`）: git の commit・ブランチ・未コミットの変更の有無と、`git diff HEAD` の SHA-1 の先頭 12 文字（同じ変更なら同じ値。開発中は常に未コミットの変更があるので commit だけでは版が区別できない）、`APP_ENV`、control・small_goals・step_picker・failure_routing、Gemini・Jev・ローカル LLM のモデルと振り分け、定石の段の名前。14 個の `JsonlWatchRecorder` はそれぞれ起動時刻でファイル名をつけるので、実行の番号は共有しない。集計は時刻で、終わった時刻より前で一番新しい実行に結びつける。

## 3. 集計（`tools/goal_outcomes.py`）

```bash
python tools/goal_outcomes.py                              # 日ごと
python tools/goal_outcomes.py --by run                     # 実行（commit・設定・モデル）ごと
python tools/goal_outcomes.py --by kind --since "2026-10-03 00:00"   # 目標の種類ごと
python tools/goal_outcomes.py --kind "have(food" --by day  # 食料だけを日ごとに
python tools/goal_outcomes.py --from-log data/logs/*.zip data/logs/ailoveshen-dev.log   # 記録の前の分を補う
```

列: 件、達成、失敗、死亡、切、成功率、達成/時、死亡/時、歩（中央）、秒（中央）。`--by` は day / hour / run / kind / predicate / source（生存か大目標か）/ all。`--json` は機械向け。

`--from-log` は記録が始まる前の分を、メインログの `_start_goal` の行から作る（.zip も読む）。目標の秒数は次の目標の行までの間隔で、歩数は分からない（`steps` は null）。`logs/goal_ends` に記録のある期間は二重に数えない（記録の最初の時刻より前の分だけ足す）。

## 5. 限界

- 観察のログなので再生できない。世界の状態は残らず、「同じ状況で変更後にやり直す」ことはできない。変更の効果は統計の比較にとどまり、実行ごとの揺れ（世界、時間帯、LLM の非決定）が大きい
- `seconds` は Gemini・Jev の決定の待ち、反射の待ちを含む。止まっていた間は含まない（目標の秒数の合計で割る）。引き継いだ小目標は続きから測る（実機の最初の記録で、昨日の `set_at` から測って 22 時間になっていたのを直した）。`resumed` を書く前の版の記録は、3 時間を超える秒数を集計が使わない（実測の最大は 52 分）。目標の決定が失敗して小目標が残ったときの重複記録は、ベンチマークの最初の本番で見つけて直した（1 つの小目標を 1 回だけ記録する。それ以前の記録には同じ `started_at` の重複行がある。設計書 83 §7.3）
- `steps` は新しい記録からだけ。過去分（`--from-log`）は null
- 小目標の達成を数えるだけで、大目標の達成（家が建った、畑ができた）は数えない
- `達成/時`・`死亡/時` は小目標の秒数の合計で割る。小目標の間の決定の待ち（Gemini・Jev・計画の LLM。設計書 51 では待ちの約 69%）は入らないので、LLM の決定を遅くする変更は、この列では動かない（実行の始まりから終わりまでの実時間で割る列が要るなら足す）
- 判断の質（Jev がよい手を選んだか）は、この記録からは取れない。`logs/steps` の `ok` は「実行できた」であって「よい手だった」ではない

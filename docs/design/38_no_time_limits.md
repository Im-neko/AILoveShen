# 設計書 38: 行動を時間で止めない

## 1. きっかけ

ユーザー（2026-09-27）:「20 秒の制限は何のため？なくても良いと思う。移動もそうだけど基本制限は不要です。必要になったら野営です」。範囲は「すべての行動」。止めてよいのは「考え直しの依頼」「空腹・体力が危ない」「見張り（Jev）に任せる」「夕方・夜になった」。

それまでの行動には時間の上限があった（`TIMEOUTS_MS`: 既定 20 秒、移動・かまど・寝るなど 45 秒、探索 30 秒）。長い道のりは 1 回に 48m（`LEG`）だけ歩いて返し、次のステップでまた歩いた。上限の理由は 2 つ:
- Python の HTTP の読み取りのタイムアウト（60 秒）に収めるため
- 1 歩ごとにワールドを見直させるため（270m 先の家まで 45 秒以上かかった）

1 つ目は実装の都合で、2 つ目は「見直し」を時間で代用していた。区間で返すと、次のステップで Jev / Gemini がまた選び直し、別のことを始めて遠い行き先に着かないことがあった。止める必要があるのは、何かが起きたときだけ。

## 2. 止めるもの（ブリッジ、runner.mjs）

時間では止めない。行動の間 0.5 秒ごとに `needNow()` を見て、始めたときになかった必要が出たら止める:

| 必要 | 条件 | 止めない行動 |
|---|---|---|
| 夕方・夜 | 始めたときより暗い時間帯になった（昼 → 夕方・夜、夕方 → 夜。明け方・朝になるのでは止めない） | 夜を過ごす・家に入る・戦う・逃げる・食べる・松明（`NIGHT_VERBS`） |
| 空腹 | 食料が `HUNGER_URGENT`（6）以下になった（始めたときにもう以下なら止めない: 食料を探す行動を毎回止めない） | eat |
| 体力 | 体力が `HEALTH_CRITICAL`（8）以下になった（同じく始めたときより下がったときだけ） | 戦う・逃げる（`DAMAGE_TOLERANT`） |

- 結果は `failed: stopped: it is dusk now (while walking toward home (212m away); moved 83m)` のように、何をしていたか（`bot.actionPhase`）と動いた距離を添える
- ボートで水の上にいる間は見ない（岸まで漕ぐ。設計書 37 §6）
- ダメージ（`interrupted: took damage`）、反射、`POST /abort`（見張りの Jev、考え直し）は今まで通り
- 動けない・経路がないのは今まで通り移動が失敗にする（`move.mjs` の `stuck:`、No path）
- `stopped: ` と `rethink: ` の理由は、ダメージ・反射と同じく小目標の失敗・行き詰まりに数えない（`NOT_A_FAILURE`、Python の `INTERRUPTED_PREFIXES`）

## 3. 行動ごとの変更（primitives.mjs）

- `legToward`: 着くまで区間（`LEG` 48m）ごとに歩き続ける。区間ごとに先の長い水を見直し（チャンクは進むにつれて届く）、ボートがあれば渡る。9 か所の呼び出しは、区間の途中で返さなくなった
- `ride_boat` / `crossWater`: 行き先か向こう岸まで漕ぐ（`drive` の `maxMs` は既定で無限）
- `smelt`: 全部焼けるまで待つ。燃料が切れて火が消えたらやめる
- `dig_down`: 掘れる所が見えるか、下りられなくなる（`dig_depth`、溶岩・水・砂利・岩盤）まで下りる（1 回 6 段の上限をやめた）
- 刈る（草・葉）: 何か落ちるまでか `SWEEP_MAX` 本まで
- `attack`: 相手がいなくなるまで。見失った（24m より離れた）、`STUCK_MS` の間近づけない・動けないときはやめる
- `flee`: 離れたい距離まで。`STUCK_MS` の間それ以上離れられなければやめる
- 消したもの: `TIMEOUTS_MS`、`DEFAULT_TIMEOUT_MS`、`RIDE_MS`、`SMELT_WAIT_MS`、`STAIR_STEPS`、`SWEEP_MS`、`FIGHT_TIMEOUT_MS`、`FLEE_TIMEOUT_MS`、時間切れで歩いた分を成功にする `walkedOnTimeout`、進み具合の `limit_s`
- 残したもの: ドアの開け閉め・ドアを通る歩きの上限（home.mjs）、ボートを置く・乗る・降りるの待ち（boat.mjs）。どれも「動かない」を見るもので、行動の長さの上限ではない

## 4. 技（skills.mjs）

1 回 180 秒の上限をやめた。残す上限: 行動 40 回、調べもの 200 回、judge 10 回、CPU 1 秒（待っている間は数えない）、メモリ 32MB。見張り・反射・`/abort` と、中の道具の行動の止め方（§2）は同じ。

## 5. Python 側

- `MineflayerBridgeClient`: 行動を実行するリクエスト（`POST /act`、`/tool`、`/skills/<name>/run`）は読み取りを待ち続ける（`httpx.Timeout(timeout_seconds, read=None)`）。ほかは `minecraft.bridge.timeout_seconds`（60）のまま。Node の `requestTimeout`（既定 5 分）はリクエストを受け取るまでの上限で、返事を待つ間は切らない（実測）
- 考え直しで止める: 行動が長くなったので、切れ目を待つと考え直しが遅れる。`AdvancePlayUseCase._cut_on_rethink` が行動の間 0.5 秒ごとに `PlaySession.rethink_mark` を見て、増えたら `bridge.abort("rethink: <理由>")`。まだ行動が始まっていなければ（道具を選んでいる間）、始まるまで止め続ける。理由は残り、次の切れ目で Gemini が考え直す（設計書 34 §10.1）
- 道具の説明（`goto`、`ride_boat`）と技のプロンプトから、48m・20 秒・180 秒の上限を消した

## 6. 決めなかったこと・あとで

- 実機で確かめていない: 長い移動（数百 m）が 1 回で着くか、夕方で止まったあと夜の小目標に移るか
- 見張り（ToolWatcher）の「進んでいるか」の質問は、今も記録だけ（`act_on_progress`）。時間の上限がないので、進まない行動を止めるのは `move.mjs` の stuck と見張りの配信者の質問だけになる。ログ（`logs/watch`）を見て、進んでいるかの答えで止めるかを決める
- 候補モード（`--control candidates`）の候補も時間で止まらなくなった（同じ runner を通る）

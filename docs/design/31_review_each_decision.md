# 目標を決めるたびに、今の状態で見直す

作成: 2026-09-26。26（手順と Jev の小目標）、27（失敗の分析）に足す。

## 1. 目的

ユーザー（2026-09-26）: 「もっと効率がよい方法を常に模索して行動するようにしてほしい。Gemini が目標を選ぶたびに、今の状態でできることを見直してプランを修正してほしい」

## 2. 今まで

- 中目標リストの編集（plan_changes）は「普段は空」、手順（steps）は「手順がないか、うまくいっていないときだけ書く」。今の状態を見て、もっと速いやり方に直す決まりはなかった
- 目標の決定は手順を「手順:」の並びで見るだけで、どれが済んでいるか・今は手に入らないかを知らなかった（それを判定するのは Jev の GoalChooser だけ）
- 中目標の進み具合は、決める前に毎回 `/check` で判定している（`MidGoalKeeper.judge`）

## 3. 形

- **見直し（`review`）を毎回、最初に書かせる**: スキーマの最初の項目で必須（失敗のときは diagnosis → remedy → advice の次。出力はスキーマの順なので、状態を見てから編集を決める）。今の持ち物、チェスト、近くのもの、覚えている場所、時間帯、手順の今の状態から、もっと早い・無駄のないやり方（順番、手順、済んだことを飛ばす）がないか。何を変えたか、変えないならその理由を日本語 1〜2 文で
- **見直しの材料**: 一番上の中目標の手順を、決める前に `/check` で判定して本文に「手順の今の状態」として出す（済み / まだ（進み具合）/ 今は手に入らない）。ブリッジの変更は要らない
- **決まり（システム指示）**: 「見直し」の節。済んだ手順・持っている物・チェストの物は集め直さない、近くの材料や同じ外出でできることをまとめる、先に作ると速くなる道具は先に、今は手に入らない手順は手に入るようにする手順を前に入れるか後ろに回す、夜は中でできることに使う。**変えないのも答え**（理由のない入れ替えはしない。前の判断を覆すなら何が変わったかを書く、は今までどおり）。手順は「見直しでもっとよい手順が見つかったとき」も書き直す
- **見せる**: `Goal.review` に残し、`activity()` の小目標に「決めたときの見直し」として出す（実況が「チェストに木があるから先に板材にするね」と言える）。ログにも出す

## 4. やらないこと

- Gemini を呼ぶ回数を増やすこと: 見直しは Gemini が目標を決めるとき（中目標が変わった、失敗、手順が尽きた、死んだ、`replan_minutes` ごと）だけ。もっと頻繁にするなら `minecraft.agent.replan_minutes`（既定 20）を短くする
- 見直しの正しさの確かめ: 変更は今までどおりコードの決まり（リストの上限、条件の判定、手順の形）で確かめる

## 5. 検証

- 単体テスト: スキーマの順（review が最初、失敗のときは advice の次）と必須、手順の今の判定が本文に出る、`Goal.review`
- 実機: `logs` の「見直し:」の行で、手順や順番を直した回数と中身、`tools/gemini_usage.py` で出力トークンの増え方

# 街の場所（候補地の調査と引っ越し）

作成: 2026-09-25。`15_town.md` の続き。15 では街を「今の家を広げたもの」として定義させた。今の家は、スポーンした所の近くの平らな地面（`findSite` が最初に見つけた所）で、場所は考えて選ばれていない。この設計書では、街を作る場所を Gemini に選ばせる。必要なら引っ越す。

## 1. 目的

ユーザーの方針（2026-09-25）:
- 「街づくりするなら場所の選定も必要じゃない？」
- 案 2「場所ごと選び直し、必要なら引っ越す」を選んだ

今の場所で困っていること（実機で見えたもの）:
- 地表に出ている石が少ない。鉄 run では石の探索に約 50 ステップ、town3 では鉄の剣がまた石で止まった
- 家のまわりに、建物を何軒も置ける平らな土地があるかを誰も見ていない（15 の C に要る）
- 「場所を選び、理由を話す」場面は配信の見どころになる

## 2. 流れ

大目標の街の、最初の段階の前に「場所を決める」を置く。

0. **最初の家（仮の小屋）**: 設定の中目標のとおり、スポーンの近くに家を建てて最初の夜を越す
1. **調査**: 家ができたら、中目標「街の場所を探す」（`surveyed(9)`）が入る。ボットが候補地を見て回り、ブリッジが地形を数字にする（§3）
2. **選択**: 調べ終えたら、Gemini が候補地の表を見て 1 か所選び、理由を配信で話す（§4）。最初の家の場所も候補に入れる（動かない方が良ければ、そう選べる）
3. **引っ越し**: 最初の家の場所以外なら、そこに建てる家を設計し、中目標「〇〇に引っ越す」（`built()`、`placed(bed, home)`）を一番上に入れる。最初の家は「前の家」として残す（§6）
4. **街の定義**: 選んだ場所の特徴（石が多いなど）を入れて、15 §3 の定義を 1 回だけ作る（§5）
5. 準備（調査、引っ越し）が済んだら、15 のとおり段階を進める

2 と 4 は 1 回だけ。場所と定義は、決めた後は変えない（コメントでも実行のたびにも変えない）。

## 3. 調査（ブリッジ）

- 地形は読み込まれたチャンクから読む（サーバーの view distance は 8 チャンク＝約 128 ブロック）。遠くを見るには行く必要がある
- 候補地: 今の家を中心に、半径 64〜160 ブロックの 8 方向と、今の家の場所。行ったことのない方向は、1 レッグ（48m）ずつ歩いて見る
- 候補地ごとに数えるもの（その地点から半径 32 ブロック）:
  - 建てられる土地: 5x5 の家が置ける平らな区画がいくつ取れるか（今の `siteFits` を使う）、いちばん広い平らな面の大きさ
  - 資源: 地表に出ている石・石炭・鉄（空気に面したもの。`6566a6d` と同じ判定）、原木の本数
  - 水: 水源のブロック数（将来の畑、見た目）
  - 動物: 羊・牛・豚・鶏の数（記憶も使う）
  - 危なさ: 大きな段差や崖の多さ、溶岩、水面の割合（建てられない所）
  - 今の家からの距離
- 結果は記憶（`state.json`）に `sites` として残す。数字だけ（Gemini の判断は入れない）。観測の `survey` で Python に渡る
- 述語 `surveyed(n)`: n か所の候補地を調べ終えた。中目標の完了条件に使える（世界から判定できる）

## 4. 選択（Gemini）

- 調査が終わったら（`surveyed` の中目標が完了したら）、Gemini に候補地の表を渡して 1 か所選ばせる。出力は、選んだ候補地、理由（配信で話す）、街の名前
- 表の数字は §3 の数字だけ。Gemini の「平らそう」「きれい」は使わない（15 §2 の教訓: Gemini の「できる」は信じず、世界の数字で確かめる）
- 選択は `TownSiteChosenEvent` で実況する
- 視聴者のコメントで場所は変えない（13 の方針）

## 4.5 調べたこと・決めたこと（配信の文脈に残す）

ユーザーの指摘（2026-09-25）:「調べたことは目標と同じように別で整理して置いておけると良さそう」。選択のプロンプトにだけ表を渡すと、選んだ後は「なぜここに住んでいるか」を忘れる。

- **調べた事実**: ブリッジが測った候補地の数字（§3）と、いつ調べたか。書くのはブリッジだけ（`memory.sites`、`GET /sites`）。Gemini は書けない
- **決めたこと**: 選んだ候補地、理由、街の名前。Gemini が書き、`data/mission.json` に保存する（事実とは別の欄）
- 両方を `Activity` に入れ、`stream_context` の 1 つの欄として、目標の決定・実況・チャットの返答のすべてに見せる。ゴールボードにも出す
- Gemini が自由に書けるメモは作らない。推測が事実として戻り、確かめないまま強まるため（一般的な「Gemini のノート」は `18_notes.md` で別に設計する）

## 5. 街の定義（場所を決めた後に 1 回だけ）

- 承認は「場所を決めたときに 1 回だけ作り直す」（§9 の 1）。実機は新しいワールドから始める（§9 の 4）ので、場所を決める前に街はない。そこで、**街は場所を決めた後に 1 回だけ定める**ことにした（承認の範囲を狭めたもので、覆してはいない）。古い段階の中目標を終わらせる特別な経路は、使う場面がないので作らない
- 定めるときは、選んだ場所と、その場所の数字を Gemini に渡す（「石が多いので丸石の外周壁」など、場所に合った街にするため）
- 定めた後は、今までどおり固定する
- 段階の中目標は、場所が決まり、準備（調査、引っ越し）の中目標が済むまで足さない。段階の条件（`lit`、`stored` など）は家を基準に判定するので、引っ越す前の家で満たしても意味がない。並び順では守らない（Gemini が move で並べ替えられるため）

## 6. 引っ越し

- 新しい場所の家は、今の家と同じ仕組みで建てる。Gemini が設計し、ブリッジが `siteFits` で置く位置を選ぶ。ただし探す中心は、ボットのいる所ではなく選んだ候補地にする
- 建て終わるまでは、今の家が「家」のまま（夜はそこで寝る）。建て終わった時点で、新しい家が `state.home` になる。今の家は `state.formerHomes` として残す（そこのチェストの中身は記憶に残る）
- 荷物: `stored(...)` は「家（街）のチェストにあるもの」を数えるように直す（今は記憶にある全部のチェストを数えている）。前の家のチェストにある物は、ソルバーが取り出す元として使える（今の `withdraw` と同じ）。これで `stored(food, 16)` のような条件があれば、前の家から運ぶ手順が自然に出る
- 遠い: 候補地は最大 160m 先。移動は今の 48m レッグで足りる。夜に前の家まで戻れない距離のときは、新しい家の完成を急ぐか、前の家で寝るかを Gemini が選ぶ（今の `at_home` の判断と同じ）

## 7. 構成

| 場所 | 追加・変更 |
|---|---|
| bridge | `survey.mjs`（候補地 9 か所の数え方）、`surveyed(n)` 述語（家が要る。候補地は家を中心に 1 回だけ決める）、`survey` の候補とプリミティブ（48m レッグで行き、24m 以内で数える）、記憶の `sites`、観測の `survey`（調べた候補地の数字）、建築計画の `site`（そこまで歩いてから建て始める）と `design`、`settleHome`（別の場所に建て終わったら引っ越し、前の家は `state.formerHomes`。掘らない・置かない所に含める）、`stored` を家のチェストだけにする |
| domain | `GoalPredicate.SURVEYED`（中目標の条件にはなるが、LLM が書ける条件 `PLANNABLE_CONDITIONS` には入れない）、`TownSite`（決めたこと）、`MidGoal.prepares_town`（調査と引っ越し。やめられない）、`MidGoalPlan.site` / `choose_site`（一度だけ）、`TownSiteChosenEvent`、`Activity.site` |
| application | `TownPlanner.advance`（小目標の切れ目で、中目標の判定の後に呼ぶ: 調査の中目標 → 選択 → 引っ越し → 定義。世界とプランから次の手順を決めるので、再起動しても続きから進む。LLM が使える答えを出せなければ次の切れ目でやり直す。代わりの場所では進めない）、`HouseDesigner`（家の設計を `house.py` に切り出し、最初の家と引っ越し先で共有）、`MidGoalKeeper.add_town_goal`、`StartPlay` は建築計画の状態から家と完成の告知を決める（引っ越しの途中で再起動しても新しい家を名乗る） |
| infrastructure | 場所の選択のプロンプト、家の設計と街の定義に場所を渡す、`stream_context` に「街の場所（決めたこと）」と「調べた候補地（ブリッジが測った数字）」を分けて出す（目標の決定、実況、返答のすべて）、保存（`data/mission.json` に `site` と `prepares_town`） |
| presentation | ゴールボードに `site` と `survey`、オーバーレイに調査の進み具合と街の名前、ナレーターが選んだ場所と理由を話す |

## 8. 検証

- 単体テスト: 候補地の数え方（平らな区画、地表の資源、水、崖）、`surveyed`、選択の検証（表にない場所は断る）、定義のやり直しが 1 回だけ、`stored` が街のチェストだけを数える
- 実機: 調査 → 選択 → 定義 → 新しい家の完成までを、介入なしの自律実行で通す

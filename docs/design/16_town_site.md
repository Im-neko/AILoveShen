# 街の場所（候補地の調査と引っ越し）

作成: 2026-09-25。`15_town.md` の続き。15 では街を「今の家を広げたもの」として定義させた。今の家は、スポーンした所の近くの平らな地面（`findSite` が最初に見つけた所）で、場所は考えて選ばれていない。この設計書では、街を作る場所を Gemini に選ばせる。必要なら引っ越す。

## 1. 目的

ユーザーの方針（2026-09-25）:
- 「街づくりするなら場所の選定も必要じゃない？」
- 案 2「場所ごと選び直し、必要なら引っ越す」を選んだ

今の場所で困っていること（実機で見えたもの）:
- 地表に出ている石が少ない。鉄 run では石の探索に約 50 ステップ、town3 では鉄の剣がまた石で止まった
- 家のまわりに、建物を何軒も置ける平らな土地があるかを誰も見ていない（15 の C に要る）
- 「場所を選び、理由を話す」場面は配信の見どころになる

## 2. 流れ

大目標の街の、最初の段階の前に「場所を決める」を置く。

1. **調査**: ボットが候補地を見て回り、ブリッジが地形を数字にする（§3）
2. **選択**: Gemini が候補地の表を見て 1 か所選び、理由を配信で話す（§4）。今の家の場所も候補に入れる（動かない方が良ければ、そう選べる）
3. **街の定義をやり直す**: 選んだ場所の特徴（川沿い、石が多いなど）を入れて、15 §3 の定義を 1 回だけ作り直す（§5）
4. **引っ越し**: 新しい場所に家を建てる。今の家は「前の家」として残す（§6）
5. 以降は 15 のとおり、段階を進める

2〜3 は 1 回だけ。場所と定義は、決めた後は変えない（コメントでも実行のたびにも変えない）。

## 3. 調査（ブリッジ）

- 地形は読み込まれたチャンクから読む（サーバーの view distance は 8 チャンク＝約 128 ブロック）。遠くを見るには行く必要がある
- 候補地: 今の家を中心に、半径 64〜160 ブロックの 8 方向と、今の家の場所。行ったことのない方向は、1 レッグ（48m）ずつ歩いて見る
- 候補地ごとに数えるもの（その地点から半径 32 ブロック）:
  - 建てられる土地: 5x5 の家が置ける平らな区画がいくつ取れるか（今の `siteFits` を使う）、いちばん広い平らな面の大きさ
  - 資源: 地表に出ている石・石炭・鉄（空気に面したもの。`6566a6d` と同じ判定）、原木の本数
  - 水: 水源のブロック数（将来の畑、見た目）
  - 動物: 羊・牛・豚・鶏の数（記憶も使う）
  - 危なさ: 大きな段差や崖の多さ、溶岩、水面の割合（建てられない所）
  - 今の家からの距離
- 結果は記憶（`state.json`）に `sites` として残す。数字だけ（Gemini の判断は入れない）
- 述語 `surveyed(n)`: n か所の候補地を調べ終えた。中目標の完了条件に使える（世界から判定できる）

## 4. 選択（Gemini）

- 調査が終わったら（`surveyed` の中目標が完了したら）、Gemini に候補地の表を渡して 1 か所選ばせる。出力は、選んだ候補地、理由（配信で話す）、街の名前
- 表の数字は §3 の数字だけ。Gemini の「平らそう」「きれい」は使わない（15 §2 の教訓: Gemini の「できる」は信じず、世界の数字で確かめる）
- 選択は `TownSiteChosenEvent` で実況する
- 視聴者のコメントで場所は変えない（13 の方針）

## 4.5 調べたこと・決めたこと（配信の文脈に残す）

ユーザーの指摘（2026-09-25）:「調べたことは目標と同じように別で整理して置いておけると良さそう」。選択のプロンプトにだけ表を渡すと、選んだ後は「なぜここに住んでいるか」を忘れる。

- **調べた事実**: ブリッジが測った候補地の数字（§3）と、いつ調べたか。書くのはブリッジだけ（`memory.sites`、`GET /sites`）。Gemini は書けない
- **決めたこと**: 選んだ候補地、理由、街の名前。Gemini が書き、`data/mission.json` に保存する（事実とは別の欄）
- 両方を `Activity` に入れ、`stream_context` の 1 つの欄として、目標の決定・実況・チャットの返答のすべてに見せる。ゴールボードにも出す
- Gemini が自由に書けるメモは作らない。推測が事実として戻り、確かめないまま強まるため（一般的な「Gemini のノート」は `18_notes.md` で別に設計する）

## 5. 街の定義のやり直し

- 15 §7 の 1 で「定義は一度だけ作って固定する」と承認をもらっている。**場所を決めたときに 1 回だけ作り直す**ことを、ここで例外にしたい（承認がほしい点 1）
- 作り直すときは、選んだ場所と、その場所の数字を Gemini に渡す（「石が多いので丸石の外周壁」など、場所に合った街にするため）
- 作り直した後は、今までどおり固定する。それまでに済んだ段階の「できたこと」（`stage_met`）は捨てる（場所が変わると `lit` などの意味が変わるため）

## 6. 引っ越し

- 新しい場所の家は、今の家と同じ仕組みで建てる。Gemini が設計し、ブリッジが `siteFits` で置く位置を選ぶ。ただし探す中心は、ボットのいる所ではなく選んだ候補地にする
- 建て終わるまでは、今の家が「家」のまま（夜はそこで寝る）。建て終わった時点で、新しい家が `state.home` になる。今の家は `state.formerHomes` として残す（そこのチェストの中身は記憶に残る）
- 荷物: `stored(...)` は「家（街）のチェストにあるもの」を数えるように直す（今は記憶にある全部のチェストを数えている）。前の家のチェストにある物は、ソルバーが取り出す元として使える（今の `withdraw` と同じ）。これで `stored(food, 16)` のような条件があれば、前の家から運ぶ手順が自然に出る
- 遠い: 候補地は最大 160m 先。移動は今の 48m レッグで足りる。夜に前の家まで戻れない距離のときは、新しい家の完成を急ぐか、前の家で寝るかを Gemini が選ぶ（今の `at_home` の判断と同じ）

## 7. 構成

| 場所 | 追加・変更 |
|---|---|
| bridge | `survey.mjs`（候補地の数え方）、`surveyed(n)` 述語、調査の候補（候補地へ 1 レッグ歩く）、記憶の `sites`、`findSite` の中心を指定できるように、`state.formerHomes`、`stored` を街のチェストだけにする |
| domain | `GoalPredicate.SURVEYED`、`TownSite`（候補地の数字）、`TownSiteChosenEvent`、`MidGoalPlan` に選んだ場所 |
| application | 場所の選択（`TownPlanner` に、候補地の表 → 選択 → 定義のやり直し）、「場所を決める」を最初の中目標に入れる |
| infrastructure | 選択のプロンプト、保存（`data/mission.json` に場所） |
| presentation | ゴールボードに候補地と選んだ場所 |

## 8. 検証

- 単体テスト: 候補地の数え方（平らな区画、地表の資源、水、崖）、`surveyed`、選択の検証（表にない場所は断る）、定義のやり直しが 1 回だけ、`stored` が街のチェストだけを数える
- 実機: 調査 → 選択 → 定義 → 新しい家の完成までを、介入なしの自律実行で通す

## 9. 決まったこと（2026-09-25）

1. 場所を決めたときに、街の定義を 1 回だけ作り直す: 承認
2. 候補地: 半径 64〜160m の範囲で承認。実装は **96m**（行き来が 2 レッグで済む）、8 方向＋今の場所の 9 か所
3. 今の家は「前の家」として残す: 承認
4. town3 は止めて実装に移る: 承認。実装後の実機は **新しいワールドで最初から**、流れは **B: 仮の小屋 → 調査 → 選択 → 必要なら引っ越し**（最初の夜はスポーン近くの小屋で越す。選んだのが小屋の場所なら引っ越さない）
5. 調べたこと・決めたことを別の欄に置く（§4.5）: 承認

## 2. 方針: 覚えさせず、引かせる

プレイする LLM（Qwen3.6、考えない）は、プロンプトに書いた決まりや知識をよく読み落とす（設計書 46: 状態の行を無視した、時間帯を取り違えた）。一方、道具の呼び出しは崩れない（設計書 36 §7）。そこで、知識と「できること」を固定の文から検索の道具へ移していく:

- プロンプトには「困ったら・知らなければ検索する」と道具の一覧だけ
- 施設、覚えた場所、アイテムの取り方、作れる物、できること（やり方）を、その場で引かせる
- 検索語から一覧のどれかを選ぶのは Jev（ユーザーの指定）。選ぶ前の絞り込みと、答えの中身はコード（世界とデータから）

## 3. 検索の仕組み（1 つ作って使い回す）

`KeySearch`（application）:
1. 一覧を作る: `{key: 短い説明}`（道具ごとにコードが作る。施設、場所、アイテム、やり方）
2. 絞り込む: 一覧が多いとき、検索語との語の重なり（英語の語、日本語は文字の 2-gram）で上位 `SEARCH_CHOICES`（16）件に。どれにも重ならなければ一覧の先頭（近い順など、道具ごとの並び）
3. Jev に聞く: `CHOICE`。選択肢は A, B, …（`GoalChooser` と同じ）と「none: どれも当てはまらない」。指示は「検索語に一番合うもの」
4. 答え: 確信度 `min_confidence`（0.5）以上なら、そのキーの中身（道具ごとにコードが書く）を返す。none なら「見つからない」と、近いものの名前を 3 つ
5. Jev が遅い（`timeout`）・答えない・迷う: コードの絞り込みの上位 3 件の中身を「確かではない候補」として返す（何も返さないより、LLM が選べる）
6. 記録: `logs/search/*.jsonl`（道具、検索語、選択肢、Jev の答えと確信度、返したキー、かかった時間）

1 ステップに調べものは 3 回まで（`MAX_QUERIES_PER_STEP`）。検索の道具が増えるので 5 回に上げる。

## 4. 検索の道具

| 道具 | 一覧（キー） | 返すもの | どこで |
|---|---|---|---|
| `search_facility {query}` | 施設の登録（§5） | 名前、種類、区画、座標の範囲、入口、中身（畑なら作物と数、熟した数）、状態（予定・建設中・完成） | 一覧はブリッジ `GET /facilities`、選ぶのは Python |
| `search_memory {query}` | 覚えた場所（資源の種類ごと、死んだ場所、チェスト、かまど） | 場所、距離、方角、いつ見たか、取れる物 | 一覧はブリッジ `GET /memory`（種類ごとに 1 件、近い 5 か所）、Python |
| `item_info {query}` | アイテムとブロックの名前（1.21.4 の全部） | 取り方: 掘る（どのブロックから、要る道具）、倒す（どのモブ）、作る（レシピ）、焼く、育てる。置けるか、食べられるか | 一覧と中身はブリッジ `Knowledge` / `RecipeIndex`（`GET /items?query=`）、選ぶのは Python |
| `uses_of {item}` | — | その素材を使うレシピ（逆引き）。`have: true` なら今の持ち物で作れる物 | ブリッジ `RecipeIndex`（検索語は正確な名前。`item_info` で確かめる） |
| `search_abilities {query}` | やり方の帳（§4.1） | 何ができるか、どの道具・目標で、手順、気をつけること | Python（`src/ailoveshen/infrastructure/adapters/prompts/abilities.yaml`） |

### 4.1 やり方の帳（できることの検索）

`src/ailoveshen/infrastructure/adapters/prompts/abilities.yaml`（`data/` は実行時のファイルの置き場で git から外れているので、プロンプトの隣に置く）: 1 項目 = `key`、`title`（日本語）、`words`（英語の検索語）、`when`（どんなときに）、`how`（道具・目標・手順を数行）、`tools`（how で使う道具）、`see`（関連する項目）。今ある機能から書く（例: 畑を作る、畑を広げる、苗木を植える、ボートで渡る、肉を焼く、夜を越す、整地する、施設を設計する、建物を建てる、技を書く、チェストにしまう・出す、壊れた道具を作り直す）。機能を足したら帳にも足す（CLAUDE.md の決まりにする）。

今の固定の「できること」（`ABILITIES`）は残す（街の定義・段階の書き直しが語彙の版に使う）。道具の選択のプロンプトからは、やり方の説明を少しずつ帳へ移す（プロンプトが短くなる）。

## 5. 施設の登録（ブリッジ、`state.facilities`）

1 つの施設 = `{ name, kind, zone, box: {min, max}, entrance?, layout, status, createdAt }`。
- `kind`: `home`、`build`、`farm`、`tree_farm`、`mine`、`pen`（動物の囲い）、`trap`
- `zone`: 理想図の区画 id（§6）。区画の外の施設はない（作るときに確かめる）
- `layout`: 種類ごとの配置（§7）。ワールドの座標で持つ（Python は持たない: 座標の持ち主はブリッジだけ）
- `status`: `planned`（設計した）、`building`、`done`
- `GET /facilities`（一覧と今の中身）、`PUT /facilities/<name>`（登録、確かめて断るときは 400 と理由）

今ある物を施設として取り込む（最初の起動で）:
- 家（`state.home`）→ `home`
- 名前付きの建物（`state.builds`）→ `build`
- 家の畑（`state.memory.farm` と、家のまわりの耕地）→ `farm`（名前 `home_farm`）
- 植えた苗木（`state.plantings`）→ 近いものをまとめて `tree_farm`（名前 `tree_farm_1`…）

取り込まないと、最初の理想図が今の畑の上に別の区画を描き、畑を忘れる。

## 6. 街の理想図（マスターデータ、`data/mission.json`）

- 区画の表: 街の中心（街の場所。最初の家なら家の扉）から `TOWN_CELLS` x `TOWN_CELLS`（12 x 12）の区画、1 区画 `ZONE_SIZE`（8）ブロック四方（96 x 96）。区画 id は列 A〜L・行 1〜12（地図の画像と同じ呼び方）
- 各区画: `{ id, box: {min_x, min_z, max_x, max_z}（ワールドの座標）, use, facility? , note }`。`use` は `home`、`residence`、`farm`、`tree_farm`、`mine`、`pen`、`trap`、`storage`、`workshop`、`plaza`、`road`、`free`（空き）、`unusable`（水・崖・溶岩）
- 作るとき: 街の定義のあと（`TownPlanner`）に 1 回。材料は、区画ごとの地形（ブリッジの `GET /map` の数字: 平らさ、水、溶岩）、今ある施設（§5 で取り込んだもの）、街の定義と段階。今ある施設の区画は固定（描き直しで動かさない）
- 見直すとき: 街の段階が進んだとき、施設の区画が足りないとき（理由を付けて記録。`history`）。それ以外は変えない
- 見せ方: ローカルの LLM には文（区画 id、用途、施設の名前だけを 1 行ずつ。空きはまとめる）。ゴールボードに画像。建物の設計（Gemini）の地図にも区画の枠を描く
- 目標の決定と施設の設計のプロンプトの「今していること」に、理想図の要約（用途ごとの区画と施設、空き区画の数）を入れる（システム指示には入れない: 8000 字の上限、26 §4）

## 7. 施設の設計（配置図 → 作る）

施設を作る中目標（`facility(name)` の条件）を足すと、`BuildDesigner` と同じく先に設計させる（`FacilityDesigner`、`purpose=facility_design`、ローカルで考える）。設計は種類ごとの小さな形で、コードがブロックと場所に展開する。場所は理想図の区画（`zone`）で選ばせ、座標はコードが区画の範囲から決める。

| 種類 | 設計で決めること | 展開（layout） | 完了（`facility(name)`） |
|---|---|---|---|
| `farm` | 区画、作物、広さ（幅 x 奥行き、9 まで）、水の置き方（真ん中の 1 列か 1 マス） | 耕地のマス、水のマス、柵なし | 耕地がすべてあり、水があり、作物が植わっている |
| `tree_farm` | 区画、苗木の種類、本数、間隔（2〜4） | 苗木を植えるマス（格子） | すべてのマスに苗木か木 |
| `mine` | 区画、入口の向き、目標の深さ（y）、幅（1〜2） | 入口のマス、階段の列、下の作業場の範囲 | 目標の深さまで階段が通っている |
| `pen` | 区画、広さ、入れる動物 | 柵の列、門 | 柵が閉じている（動物を入れるのは別の目標） |
| `trap` | （§8） | — | — |

今の目標との関係（リリース前なので、互換は取らずに置き換える）:
- `farmed(crop, n)` は「施設の畑の中で」数える。`where` に施設の名前（省略すると、その作物の畑の施設のうち一番近いもの。なければ家の畑 `home_farm`）
- `planted(sapling, n)` も同じく植林場の中で数える
- 道具 `plant` / `till` / `sow` は、場所を渡されなければ、施設の配置の空いたマスから選ぶ（今の「家から 6〜24 m」の探し方はやめる）
- 採掘場: 石・鉱石を探すとき、完成した採掘場があればそこから下りる候補を先に出す

## 8. 今は作れないもの（動物の囲い・トラップ）

- **動物の囲い**: 柵（`oak_fence`）と門（`oak_fence_gate`）を置く形は、今の建物の材料（板材・原木・丸石・土）にない。足せば柵は作れる。ただし動物を中に入れる行動がない（リード `lead` で連れて来る、小麦を持って誘う）。囲いを作っても空のまま
- **トラップ**（モブトラップ、アイアンゴーレムトラップなど）: 湧き層・水流・落下・ホッパーの仕組みで、どれも今の形（直方体）と材料で書けない。水流の向き、湧き潰しとの両立、ホッパーとチェストのつなぎ方が要る
- この 2 つは、畑・植林場・採掘場ができてから、足りない能力（柵と門、動物を連れて来る、水を置く・汲む、ホッパー）を別の設計書にして進める。理想図には区画（`pen`、`trap`）だけ描ける

## 12. 実装で分かったこと（2026-09-28）

- **日本語の検索語**: 一覧の説明は英語（ブリッジの名前）なので、「鉄」「小麦の畑」が語の重なりで 1 つも当たらず、正解が 16 件の外に切り捨てられることがあった。ゲームの `ja_jp.json`（misode/mcmeta の `<版>-assets`、`npm run recipes:fetch` が `data-static/names-ja-<版>.json` に取る）の日本語名をブリッジが添え（アイテム、作物、覚えた場所の種類、取れる物）、施設の種類の日本語は Python（`KIND_JA`）が添える。語の集まりに漢字 1 文字も入れる（「鉄」で「鉄鉱石」）
- **覚えた場所は種類ごとに 1 件**（キーは種類の名前、中身は近い 5 か所）: 場所 1 つずつでは 16 件をすぐ超える
- **絞れていないとき**: どの項目とも語が重ならず一覧が 16 件を超えるなら、切り捨てたことと、別の語（英語の名前）で検索し直すことを返す。語が重ならない候補の中身（座標）は返さない（弱いモデルは返った座標へそのまま歩く）。語が重なる候補だけを「確かではない候補」として中身つきで返す
- **完全一致**: キーと同じ検索語（大文字・空白の違いは見ない）は Jev に聞かずに返す
- **実測**（本物の Jev、item_info とやり方の帳、2026-09-28）: パン→bread、かまど→furnace、羊毛→white_wool、水を渡りたい→cross_water、鉄が欲しい→mine_ores、道具が壊れた→upgrade_tools。「鉄」は鉄の付く物が多く確信度 0.49（語の上位 3 件を返す）、「木の棒」は none（日本語名は「棒」）
- **帳のずれ**: `tests/unit/application/test_search.py` が、帳の `tools` が道具の一覧にあり `how` に書かれていること、`see` が実在することを確かめる（書いた時点で 2 件の食い違いを見つけた）

## 14. 段階 4A: 施設の設計と `facility(name)`（2026-09-28）

- 述語 `facility(name)`（条件、小目標、スキルの `expects`）: 畑は全部のマスが耕地で作物が植わっている、植林場は全部のマスに苗木か木。まだない名前は判定できない（`NotYetError`）ので、中目標に足す前に設計する
- ブリッジ `PUT /facilities/<name>` `{kind, zones, boxes | near_home, purpose, design}`: 区画の中から実際のマスを選ぶ（畑: 高さ ±1 にそろった w x d の四角を両方の向きで探す。植林場: 間隔 `spacing` の格子を中心に近い順）。耕せない・植えられない所（家とまわり、建物、ほかの施設）は除く。直せば通る理由は 400（`GoalRejectedError`、設計をやり直す）、区画の半分以上が読み込まれていないときは 409（`FacilityAreaNotReadyError`、やり直しても直らないので設計できないとする）。`GET /facilities` は状態（planned / building / done）も更新する
- 小目標 `facility(name)` の葉は、次のマスを耕す・まく・植える候補になる（`nextCell`）。道具 `till` / `sow` / `plant` は x,y,z を省くとその施設の次のマス。耕す前に草花を刈る
- Python `FacilityDesigner`（`purpose=facility_design`、ローカルで考える、3 回まで）: 理想図にその名前の予定の区画があればそれを見せ、選べる空き区画と地形を並べる。答え（種類、区画、作物・大きさ / 苗木・本数・間隔）はコードが確かめる（区画が 1 つの四角か、固定やほかの施設の区画でないか、種類ごとの項目）。登録できたら理想図のその区画に施設を書き込み、前に予定した区画で使わなかったものは空きに戻す。理想図がまだなければ家のまわり（`near_home`: 家の中心から ±24）
- `MidGoalKeeper` は建物・判定と同じく、足す中目標（配信者の編集、視聴者の頼み、街の段階）にまだない施設があれば先に設計させる。設計できなければ `FacilityNotDesignedError`（`BuildNotDesignedError` の一種）で、決定の残りは通し、その中目標と手順だけ落とす
- §7 の表からの変更: 畑の辺は 16 まで（1 区画 8 に 2 区画）。植林場の間隔は 4〜6（植える規則 `TREE_GAP` 4 より狭いと植えられない）。**水はまだ置かない**（水を汲む・置く能力がない。耕地は作物が植わっていれば乾いても土に戻らないが、育ちは遅い）
- 述語が増えたので `vocabulary_version` が変わる: 次に始めたとき、今の段階の未解決の部分が 1 度書き直される（設計書 15）
- 設計できたあとで決定がほかの理由（手順の順番、もう済んでいる、リストがいっぱい）で差し戻されると、施設は planned のまま区画を持ち続ける（建物も同じ）。次の描き直しでその区画は固定になる。実機で困るようなら、使われない planned の施設を片づける

## 15. 段階 4B: 作物と植林は施設で数える（2026-09-28）

- 家から 6〜24 m の輪で場所を選ぶこと（`plantSpot` / `tillSpot` / `sowSpot`、`homeFarm`）をやめた。§7 の「一番近い施設」もやめた（ボットの位置で残りが変わり、停滞の判定が揺れる）
- `farmed(crop, n)`: その作物の設計した畑（設計のマス）と、家の畑（家のまわりの、設計した畑の外の耕地: 前からある畑）の合計（`cropFarms`）。読み込まれていない畑は最後に見た数（`state.memory.farms[施設][作物]`）。家から遠い区画の畑も数える（前は家のまわり 32 m しか見ていなかった）
- `planted(sapling, n)`: 今までどおり植えた場所の合計（取り込んだ植林場も含む）
- 新しく耕す・植えるのは設計した施設のマスだけ（`workCell`）。まくのは家の畑の空いた耕地も。道具 `till` / `plant` はほかのマスを断り、`sow` はほかの作物の畑を断る。x,y,z を省くと、今の小目標の施設か、その作物・苗木の施設の次のマス
- 畑・植林場がない → `blocked` と `impossible`「facility(<name>) で先に作る」。n が空きより多い → 「別の名前で足す」（空きが 0 なら `impossible`）。畑が見えていないとき空きが最後に見た数なら、畑へ行く（`go_facility`）
- ソルバーの `growing`: 空きがあればまく・耕す（`also`）と `farmed(crop, 植わった数 + 空き)`、なければ「facility で別の名前の畑を足す」。熟していれば `go to the farm`
- できた施設は広げられない（`registerFacility` は同じ名前を断り、設計は知らない名前だけ）。「広げる」と言うと、モデルが同じ `facility(name)` を書き、すぐ済んだものとして返されて回った（弱いモデルは言われたとおりにする）。増やすときは別の名前（`wheat_farm_2`）。広げる設計は要るようになったら
- `/observe` の `farm` は作物ごとに空きと畑の名前つき、プロンプトでは「畑」
- 進める手が 1 つもなく今は手に入らない部分がある小目標（畑がないのに `farmed` など。再起動後の保存した中目標・街の段階によくある）は、`PUT /goal` の状態の `dead_end`（理由）で、目標の決定が行き詰まるまで回さずに差し戻す

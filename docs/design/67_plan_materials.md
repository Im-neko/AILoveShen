# 67. 計画の材料の思い込み: 例文の写しをやめ、材料の木で検算する

2026-09-30。状態: 実装済み、実機では未確認（ブリッジと Python の再起動が要る）。

## 1. 何が起きていたか

user（2026-09-30）: 「鉄インゴットがチェストの為。と小目標に書かれていますが、マイクラでチェストに鉄インゴットは
不要です。この辺の勘違いってどうしたら減らせるでしょうか？」

- `data/mission.json` の中目標 j39「拠点の整理と安全の再確認」の小目標 1 が `have(iron_ingot, 3)`、理由
  「チェストを作るための鉄インゴットを確保する」。ブリッジの判定（`progress`）には正しい木が出ていた
  （`chest ← 8 planks ← oak_log`）が、計画を書く段階の LLM はそれを見ていない。bot は実際に、その小目標のために
  鉄鉱石へ階段を掘っていた。
- 原因の 1: 計画のプロンプトの例文（`PLAN_TEMPLATE`）が `have(bucket, 1)（前提 have(iron_ingot, 3)）` だった。
  数の 3 まで同じ。規則の文にも「バケツの前に鉄。鉄がなければその前に鉄鉱石」とあった。
- 原因の 2: 計画は道具を呼べない JSON 生成（`purpose=plan`）で、材料は LLM の記憶だけが頼り。コードは名前が
  実在するかしか確かめず、「その物の材料か」は確かめていなかった。

## 2. 決めたこと

1. **例文の写しをやめる**: 例は品目を伏せ字（`<A>〜<E>`）にし、「この例の物は書かない」と添えた。前提の規則は
   「その小目標の物のレシピが直接使う材料と道具だけ。思い込みで足した物は集めに行ってしまう」に。
2. **材料の木を事実として渡す（差し戻しの文に）**: ブリッジの `/check` は `materials: true` のとき、`have` /
   `placed` / `stored` の条件にその物の材料の木を添える（`goals.mjs` `materialsOf`: ソルバーを持ち物・チェスト・
   作業台なしで走らせ、木に出るアイテムを集める。`root` はその物そのもの、`all` は道具や作業台も含む木すべて。
   家がなくて判定できない条件、木を作れない物には付かない）。計画は小目標を書く前には何を書くか分からない
   ので、渡すのは書いたあと、差し戻しの文の中（「placed(chest, home) needs chest, crafting_table, oak_planks」）。
3. **コードで検算する（`plan_lint.unneeded_materials`）**: 中目標の小目標・前提の `have(X)` で、その中目標の
   ほかの条件（と、大目標の条件のうち材料になる物）のどの木にも X の `root` が出てこないものを差し戻す。
   中目標の条件そのもの（その段階が届く先）は疑わない。ほかの条件に木がないもの（畑、整地、建物、施設…）が
   1 つでもある中目標は、何が要るか分からないので確かめない（間違いを止めるだけで、正しい計画を止めない）。
   `JobPlanner` が使う（3 回の試行の枠の中）。Gemini の目標の決定が中目標を書き直すとき（`_decide_goal`）は、
   材料の木を持っていないので確かめない。

## 3. 採らなかったこと

- 「物を作るときは必ずレシピを引く」の規則: 計画は道具を呼べない。引かせると 1 回 5〜8 秒の呼び出しが増え、
  思考なしのローカルモデルは、知っていると思っていることには規則を守らない
- 前提を LLM に書かせず solver に任せる（`next_step` の連鎖）: 設計書 50 §18 の計画の作りが変わる大きな
  変更。まず検算で誤りを止め、残るなら検討する
- 材料の木を持ち物ありで作る: 持っている物は木に出ない（すでにあるので「要らない」と誤って差し戻す）ので、
  静的な木にした

## 4. 実機で見ること

- 計画の差し戻しに `is not needed for the rest of the job` が出て、直された計画が通る
- 正しい計画が止まらない: `計画を書けなかった` が増えていないか（`logs` の `unneeded` を含む警告）
- 今の j39 の `have(iron_ingot, 3)` は `mission.json` に残っている（書き直されるまで消えない）

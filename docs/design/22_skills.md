# B: Gemini が技を書き、確かめて覚え、直して使い回す

作成: 2026-09-26。19 §3・§9 の B の詳細。A（設計書 21、`--control tools`）の道具の上に作る。

## 1. 目的

ユーザー（2026-09-25、19 §13 の 1）: A から始めて B まで必ずやる。2026-09-26: 「A はだいたい良さそうなので B の設計に入りたい」

- **直す作業を、配信の外の開発者から、配信中の Gemini に移す。** 今は行き詰まるたびにブリッジのコード（ソルバー、候補の列挙）を直している。B では、Gemini が手順を JS で書き、失敗したら理由を読んで自分で直す
- **覚える。** うまくいった手順は「技」として保存し、次からは書かずに呼ぶ。配信が長くなるほど、できることが増える（配信の見どころにもなる:「新しい技を覚えた」）
- **費用を下げる。** A は 1 ステップ（道具 1 回）ごとに Gemini を 1 回呼ぶ。技は 1 回の呼び出しで道具を何十回も呼べる

## 2. 全体の形

```
小目標（今までどおり述語。完了はブリッジが判定）
  └ Gemini の道具の選択（A のループ。1 ステップに 1 回）
       ├ A の道具を 1 つ呼ぶ（今までどおり）
       ├ run_skill(name, args)   … 覚えた技を実行する（1 ステップ）
       └ write_skill(name, what) … 新しい技を書く / 直す（別の呼び出し。書いたらすぐ試す）
技の実行（ブリッジ、サンドボックス）
  └ 技の JS が A の道具の API を呼ぶ（同じ安全の制約。断られたら理由が返る）
       ├ 見張り（ToolWatcher、Jev）は技全体を見て、止められる
       └ judge(question) で Jev に聞ける（見張りのティックで答える）
終わったら
  └ 技が宣言した「できたこと」を、ブリッジが世界から判定する → 合えば成功として数える
```

- 小目標・中目標・完了の判定は変えない（B は「どうやるか」だけ）
- 候補モード（`control: candidates`、Jev が候補から選ぶ）は比べる相手として残す。B は道具モードの中の機能
- A の道具はそのまま使える。技は A の道具の組み合わせで、A でできないことはできない

## 3. 技

### 3.1 技の形

```js
// name: hunt_nearest_animal
// description: 近くの動物（豚・牛・羊・鶏）を探して倒し、落とした物を拾う
// params: { animal?: string }            … JSON Schema（Gemini が書く）
// expects: { predicate: "have", item: "food", count: "+1" }   … できたこと（§3.3）
export default async function (t, { animal }) {
  const mobs = (await t.state()).mobs.filter((m) => !m.hostile && (!animal || m.name === animal))
  if (!mobs.length) return t.fail('no animal in sight')
  const r = await t.attack({ entity: mobs[0].id })
  if (!r.ok) return t.fail(r.result)
  await t.pickup()
  return t.done(`hunted ${mobs[0].name}`)
}
```

保存するもの（1 つの技、1 ファイル）: 名前、説明（日本語 1 文。道具の選択の一覧に出る）、引数の JSON Schema、`expects`、コード、版（直すたびに増える。前の版も残す）、使った回数・成功・失敗、最後の失敗の理由、作った日時。

### 3.2 技が使える API（`t`）

A の道具と同じ名前・同じ引数（19 §3「A の道具は B で JS から呼ぶ API と同じにする」）:

- 行動: `t.goto`, `t.dig`, `t.place`, `t.craft`, `t.pickup`, `t.attack`, `t.flee`, `t.eat`, `t.equip`, `t.smelt`, `t.deposit`, `t.withdraw`, `t.go_home`, `t.sleep`, `t.build_next`, `t.wait` → `{ ok, result, refused? }`（`POST /tool` と同じ。断られても例外にしない: 技が理由を読んで判断する）
- 調べもの: `t.find_blocks`, `t.recipe_of`, `t.how_to_get`、`t.state()`（`GET /state` と同じ書式: 体、持ち物、まわりの形、モブと id、欲求、進み具合）、`t.block_at({x, y, z})`（1 ブロックの名前）
- 判定: `t.judge(question, { kind: 'yes_no' | 'choice', options? })` → Jev の答えと確信度（§6）
- 終わり方: `t.done(summary)`、`t.fail(reason)`、`t.log(message)`（記録と、失敗したときの分析に使う）
- **ないもの**: 座標をまたいだ自由な移動の低レベル操作（キー入力）、ファイル・ネットワーク・時計・乱数以外の Node の機能。ブリッジの内部（`bot`、`state`）には触れない

`do_suggestion`（ソルバーの提案）は技からは呼べない（技はソルバーに依存しない手順にする）。`how_to_get` は調べものとして使える。

### 3.3 できたこと（`expects`）: 技が成功したかを世界で確かめる

「モデルの言い分では完了にしない」（13、15 §2）を技にも当てる。技は、終わったときに成り立つはずのことを宣言し、ブリッジが判定する:

- 条件の語彙（`have` / `stored` / `built` / `placed` / `lit`）。数は引数か相対（`"+1"`: 始めたときより 1 つ増える）で書ける
- `progress`: 今の小目標の残りの作業が減る（どの小目標のためにも使える汎用の技向け）
- `t.done()` で終わり、`expects` が成り立てば**成功**。`t.fail()`・例外・時間切れ・見張りの停止・`expects` が成り立たないのは**失敗**
- 試しの版（書いたばかり）は、1 回成功すると**確かめ済み**になる。確かめ済みの技だけが一覧の上位に出る

## 4. 技の書き方・直し方（Python）

### 4.1 書く

道具の選択で Gemini が `write_skill(name, what, reuse?)` を呼ぶと、**別の呼び出し**（`purpose=skill_write`、thinking high）で技を書かせる。道具の選択の呼び出し（thinking low、1 ステップごと）の中でコードを書かせないのは、考える深さと入力が違うため。

- 入力: API の説明（決まった文。システム指示に置いてキャッシュが効くように、26 §4）、書く技の目的（`what`）、今の小目標と状態、直近の道具の呼び出しと結果（A での試行が手順の手本になる）、似た技の名前と説明（使い回し・重複を避ける）
- 出力（JSON）: 説明、引数のスキーマ、`expects`、コード
- 受け取る前にブリッジが確かめる: 構文、`export default async function`、長さ（4,000 字まで）、`expects` の形。だめなら理由を返して書き直させる（3 回まで。今の作り直しと同じ）
- 書いたら、その場で 1 回試す（そのステップの行動になる）

### 4.2 直す

技が失敗したら、次の道具の選択に失敗が見える（どの技、どの版、理由、技の `t.log`、最後の道具の呼び出しと結果、見張りの理由）。Gemini は、もう一度呼ぶ・別の道具にする・`write_skill(name, …)` で直す（同じ名前で書くと次の版）を選ぶ。直すときは、前のコードと失敗の記録を渡す。

- 直す回数の上限: 1 つの技につき 1 時間に 3 回（費用の上限。超えたら直さずに A の道具で進める）
- 版は残す。直した版が失敗続きなら、前の確かめ済みの版に戻せる（`run_skill` の `version` 引数）

### 4.3 選ぶ

- 道具の選択のプロンプトに、技の一覧を出す: 名前、説明、引数、成功 n/m、最後の失敗。今の小目標に合うもの（`expects` の述語・品目が同じ、名前・説明が近い）を上に、最大 12 件
- 技が 20 個を超えたら、一覧の絞り込みを Jev（`Choice`）にさせるかを測る（19 §11.4 の「技の選択」）。最初はコードの絞り込みだけ

## 5. 実行（ブリッジ）

### 5.1 サンドボックス

技のコードは Gemini が書いたもので、Gemini の入力には視聴者のチャットが入りうる（目標の決定）。コードを信じない前提で、ブリッジの本体とは別に動かす:

- **案 (a) `isolated-vm`**（おすすめ）: V8 の別の isolate。Node の機能（ファイル、ネットワーク、`process`）が最初から存在しない。メモリの上限、同期の無限ループの時間切れ、外からの破棄ができる。ネイティブのモジュールなので、`npm install` でビルド（主な OS はビルド済みがある）
- 案 (b) 子プロセス: `node --permission`（ファイル・子プロセス・ワーカーを禁止）、環境変数は空（`.env` の鍵を渡さない）、IPC で道具を呼ぶ。ネットワークは Node 22 では禁止できない
- 案 (c) `node:vm` と worker: いちばん簡単だが、`vm` は安全の境界ではない（抜け道が知られている）。採らない

どれでも、技から見えるのは §3.2 の API だけで、API の呼び出しはブリッジ本体の `callTool`（A と同じ検証と安全の制約）を通る。

### 5.2 上限

| 上限 | 既定 | 超えたら |
|---|---|---|
| 1 回の実行の時間 | 180 秒 | 止めて失敗（「時間切れ」） |
| 道具の呼び出し（行動） | 40 回 | 止めて失敗 |
| 調べもの・`state()` | 200 回 | 止めて失敗 |
| `judge` | 10 回 | 止めて失敗 |
| 同期の実行（await なしで回るループ） | 50 ms | 止めて失敗（「止まらないループ」） |
| メモリ | 32 MB | 止めて失敗 |

- 反射（近くの敵、溺れ）は技より優先: 技の中の行動も今までどおり反射で止まり、技には `{ ok: false, result: 'interrupted: …' }` が返る
- `POST /abort`（見張り、Python）は技全体を止める（今の道具を止め、技の次の API 呼び出しで終わる）
- 安全の制約（夜は外に出ない、家を壊さない）は道具の側にあるので、技からも破れない

### 5.3 エンドポイント

- `GET /skills`: 一覧（名前、説明、引数、`expects`、版、成功 n/m、最後の失敗）
- `PUT /skills/<name>` `{ description, params, expects, code }`: 確かめてから新しい版として保存。だめなら 400 と理由
- `POST /skills/<name>/run` `{ args, version? }`: 1 回実行（行動が 1 つ走るのと同じ扱い: `busy`、`/state` の `action` に技の名前と今の道具、`/abort` で止まる）→ `{ ok, summary | reason, calls: [...], log: [...], expects: {met, lines}, seconds }`
- 保存場所: `minecraft-bridge/data/skills/<name>.json`（ワールドをリセットしても残す。§8 の 3）

## 6. Jev: 技の中の判定と見張り

- `t.judge(question)` は、技を止めずに Jev に聞く。ブリッジは質問を `/state` の `pending_judge` に出し、見張り（`ToolWatcher`、1 秒ごと）がその回の `system_one` に見張りの質問と一緒に入れて答え、`POST /judge` で返す。技は答えを待つ（最大 5 秒。来なければ `{ answer: null }`）。Jev の答えで世界が動くことはない（技のコードが答えを読んで道具を呼ぶ）: 19 §11.2 のとおり
- 見張りは技全体に掛かる: `run_skill` にも `intent` と `watch` の質問を付けられる（A の行動の道具と同じ）。コードの 1 問（進んでいるか）も同じ
- 技の選択を Jev に任せるのは、技が増えてから測る（§4.3）

## 7. 見せ方

- ゴールボード: `intent` に技の名前（「技: 近くの動物を狩る（v3）」）
- 新しい技が確かめ済みになったら `SkillLearnedEvent` → 実況（「狩りの技を覚えた！」）、アバターは喜ぶ
- 直したときは `SkillRevisedEvent`（実況で失敗の理由と直したことを一言）
- `/debug/gemini` に `skill_write` の呼び出し（書いたコード）が出る。`/api/skills` で一覧（読むだけ）

## 8. 決めてほしいこと

1. サンドボックス: (a) `isolated-vm`（おすすめ）/ (b) 子プロセスと Node の permission / その他
2. 上限の既定値（§5.2）と、直す回数（1 つの技に 1 時間 3 回）
3. 技をワールドのリセットの後も残すか（おすすめ: 残す。座標を決め打ちした技は引数にするよう、書く決まりに入れる）
4. 技を消せるか（おすすめ: Gemini は消さない。使わなくなった技は一覧の下に下がるだけ。消すのは開発者が手で）
5. 最初の技（おすすめ: なし。A の道具だけから始め、Gemini が覚えていくところを配信で見せる）
6. 技を書く呼び出しの深さ（おすすめ: high。費用は `tools/gemini_usage.py` の `skill_write` で見る）

## 9. 実装の順番

1. サンドボックスと API（ブリッジ）: 技を 1 つ手で書いて動かす。上限、反射、`/abort`、道具の断り。`npm test`
2. 技の保存と `expects` の判定、エンドポイント
3. Python: 道具 `run_skill` / `write_skill`、`skill_write` の呼び出し、失敗の見え方、一覧（プロンプトはシステム指示と本文に分ける）、イベント、設定（`minecraft.skills.enabled` など）
4. `judge` を見張りのティックで答える
5. 実機: A だけのときと比べる（1 時間あたりの Gemini の回数と費用、小目標の達成までの時間、技の成功率、直した回数）

## 10. 検証

- 単体テスト（ブリッジ）: API が道具と同じ結果を返す、断りが技に届く、各上限、止まらないループ、`/abort` と反射で止まる、`expects` の判定（相対の数）、版と成功の数、保存と読み込み
- 単体テスト（Python）: `write_skill` の流れ（書く → 確かめる → 試す）、書き直しの上限、失敗が次の道具の選択に見える、一覧の並び、イベント
- 実機: 食べ物探し（09-25 のログで詰まった場面）、木を切って板材にする、家のまわりに松明を置く。技を覚えて、同じ場面で Gemini の呼び出しが減るか

## 11. やらないこと

- 技から直接 Mineflayer を触る（安全の制約を通らなくなる）
- 視聴者のチャットから技を書かせる・呼ばせる（技を書けるのは Gemini の道具の選択だけ）
- 完了の判定を技の `done()` に任せる（`expects` を世界で判定する）
- 候補モード（Jev が候補から選ぶ）を消す

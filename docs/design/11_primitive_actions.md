# 根源的な行動の組み合わせ（Minecraft）

作成: 2026-09-25。`10_agent_lifecycle.md` の Minecraft への適用のうち、行動の設計。ロードマップ上は F（`09_town_building_roadmap.md`）。

## 1. 目的

M1 までは、複合アクション（`craft_bed`、`hunt_sheep`、`go_home` など）を必要になるたびに配信外で手書きしてきた。これをやめ、少数の根源的な行動の組み合わせで目標を達成する。

手書きの複合アクションの中身は3つに分かれる。

| 中身 | 例 | この設計での置き場所 |
|---|---|---|
| ① 操作の仕組み | ドアの開け閉め、レシピ本でのクラフト、ドロップを拾えるまで待つ、Paper の連打制限、中断 | 根源的な行動の実装（ブリッジ）。M1 で直したものをそのまま使う |
| ② 手順 | ベッドには羊毛3と板材3と作業台 | 依存関係のソルバー（ブリッジ）。データから導く |
| ③ その場の選択 | どの原木を掘るか、今食べるか | Jev |

## 2. スパイクの結果（`spikes/primitive_choice_eval.py`、2026-09-25）

具体的な引数つきの候補（「3m 先の oak_log を掘る」など）を 10 / 20 / 50 個並べて、Jev に1つ選ばせた。場面ごとに正解を決め、各3回測った。結果は `spikes/results/primitives/`。

| 選ぶ側 | 最初の13場面 | 後から足した7場面（ぶつかる欲求・過剰反応） |
|---|---|---|
| 規則（手書き） | 85% | 86% |
| Jev | 77〜82% | 67〜81% |
| Jev + 状態に欲求を明示 | 97〜100% | 81〜90% |
| Jev + 優先順位を指示文に書く | 97〜100% | 52% |

- **対象の選択は得意**: 近い原木、羊と牛から羊、作業台を置く、作業台でベッドを作る。候補が 50 個でも崩れず、遅延も約 0.2 秒で変わらない
- **欲求を明示すると、空腹で食べる判断は安定した**（0/9 → 9/9）。欲求は「空腹が危険（5/20）」のように数値と重さだけを書き、行動の名前は書かない
- **優先順位を指示文に書くと、過剰に反応する**: 22m 先のゾンビや 18m 先のクリーパーから、毎回逃げた
- **安全に関わる判断は、欲求を明示しても外れる**: 夜に家の中にいてベッドがないとき、外の原木を掘りに行く・ドアを開けるを 5/9 回選んだ
- 「この候補はどの小目標を進めるか」を候補の説明に書くと、かえって悪化した（Jev がそれに引っ張られて欲求を無視する）
- 参考: `rmalde/minecraft-agent`（Astra/Sol + JEV でドラゴン討伐）も、候補を出すかどうかと危険時の絞り込みはコードで行い、アクションも手書きの有界アクションだった。シードとルートを固定し、難易度は Peaceful

**結論**: Jev には「目標に関係する候補の中から、欲求を見て選ぶ」を任せる。安全に関わる判断（夜に外へ出ない、危険な敵から逃げる）は、Jev に選ばせずにコードで候補から外す。優先順位の指示文は過剰反応を起こすので使わない。

**この設計では、Jev が規則より優れていることは示せていない。** Jev（欲求を明示）が規則に勝ったのは、夜に寝る・夕方に帰る・夜に家にいるの3場面だけで、どれも規則を書いていなかったから落ちたものだった。この設計では、その3つをコードの制約と Gemini の目標に移す。Jev に残る「対象の選択」と「空腹で食べる」は、規則も全問正解している。Jev の価値は、規則を書いていない状況にどれだけ対応できるかで決まるが、それはまだ測っていない。選ぶ側は `IActionSelector` の差し替えで規則にもできるので、実機の自律実行で両方を比べて判断する。

## 3. 役割の分担

| 担当 | 決めること | 頻度 |
|---|---|---|
| Gemini | 目標（§5 の語彙の組み合わせ）、時間帯の方針（夕方は家に帰る目標を出す）、教訓 | イベント時・数分ごと |
| ソルバー（ブリッジ、コード） | 目標 → まだ満たしていない小目標の木 → 今すぐ進められる末端 | 毎ステップ |
| 候補の列挙（ブリッジ、コード） | 末端を進める具体的な行動と、欲求・脅威に関わる行動。安全の制約で外す | 毎ステップ |
| Jev | 候補の中から1つ。状態には目標、進み具合、欲求を渡す | 毎ステップ（約 0.2 秒） |
| 反射（ブリッジ、コード） | 近くの敵、水中で浮く、ドアの前の敵 | 0.2 秒ごと |

ソルバーと候補の列挙をブリッジに置く理由: レシピとドロップのデータ（`minecraft-data`）とワールドの状態がブリッジにあり、毎ステップ回すから。

**述語を判定するのはブリッジだけにする。** ブリッジは `/observe` で、目標の述語が満たされているか、小目標の木と進み具合（例: `have 3 white_wool (1/3)`）を返す。Python はそれを受け取るだけで、`have` や `built` を自分では判定しない（両側に判定があると、ずれて C になる）。

Python に残るもの:
- 目標のライフサイクル（発行、語彙の検証、停滞と予算による終了、再計画。`10_agent_lifecycle.md` §2）。停滞は、ブリッジが返す進み具合が変わらないことで判定する
- Gemini（設計図の作成と検証 `HouseBlueprint`、目標の選択）と Jev の呼び出し
- 消えるもの: `GoalType` の閉じた集合、`GOAL_ACTIONS`、`MaterialNeeds`、`HouseProject` の `goal_met` / `material_needs` / `pursuable_goals`。`HouseProject` は、目標のライフサイクルを持つ汎用の型に置き換わる

**Jev の役割（2026-09-25 ユーザーと合意）**: 何をするか（目標）は Gemini が決める。目標を達成したかの判定はコードが行う（Jev に判定させると、確実な判定が確率的になり「失敗を成功と返す」C が判定側で起きる）。Jev は、候補から次の行動を選ぶことと、コードでは書きにくい判定（続けるか切り替えるか、行き詰まっているか）を Yes/No（`Noul`）や段階評価（`Score`）で高頻度に行う。後者は、根源的な行動のループが実機で動いてから、スパイクで測って入れる。

### HTTP の約束事（ブリッジ ↔ Python）

- `PUT /goal {predicate, item?, count?, where?, distance?}` → 目標の状態。語彙にない・引数が不正・前提がない（設計図がないのに `built` など）ときは 400 と理由。目標は `data/state.json` に設計図と一緒に保存する（再起動で失わない）
- `GET /observe` → `{busy, observation, needs, goal, candidates}`
  - `goal`: `{spec, met, remaining, tree, blocked}`。`remaining` は残りの作業量（採る数・クラフト回数・置く数の合計）で、Python はこれが減らないことで停滞を判定する。`tree` は小目標の進み具合の行（例: `have 3 white_wool (1/3)`）。`blocked` は進められない理由（例: レシピがまだ解放されていない、近くに原木がない）
  - `needs`: 欲求（数値と重さだけ）
  - `candidates`: `[{id, verb, target, ...}]`。`id` は位置やエンティティ ID を含み、次の `/act` まで安定する
- `POST /act {id}` → `{ok, result, seconds}`。実行の直前に候補を列挙し直し、`id` がなければ実行しない
- `PUT /build-plan`、`GET /build-plan` は今のまま

## 4. 根源的な行動（ブリッジ）

どれも有界（時間の上限あり、`AbortSignal` で止まる）で、結果はワールドの状態で確かめて返す。失敗は失敗として返す。

| 行動 | 引数 | 中身（M1 の実装から引き継ぐもの） |
|---|---|---|
| `goto` | 位置 / ブロック / エンティティ / `home` | pathfinder、敵を避けるコスト、葉の扱い。`home` はドアの開け閉めを含む（`enterHome`）。家の中から外への移動は `leaveHome` を通る |
| `dig` | ブロック | `GoalLookAtBlock` で近づく、最適な道具を持つ、ドロップを拾えるまで待つ |
| `pickup` | 落ちているアイテム | 拾えるまで待つ。届かないものは以後出さない |
| `place` | アイテム, 位置 | 200ms の間隔、向き（ベッドは視線の向きに伸びる） |
| `craft` | アイテム, 回数 | レシピ本、100ms の間隔。3x3 のレシピは手の届く作業台が必要 |
| `attack` | エンティティ | 追って叩く（`fight`） |
| `flee` | エンティティ | `GoalAwayFrom` |
| `eat` | 食べ物 | |
| `equip` | アイテム | |
| `use` | ブロック | ドア、ベッド（寝る）。後で、かまど・チェストを開ける |
| `wait` | 秒数 | 家の中ではドアを向いて静止する（カメラが回らないように） |

M1 で直した仕組みの引き継ぎ（`actions.mjs` を消す前に、すべて根源的な行動に移す）:
- 経路の中断は `setGoal(null)`（`stop()` は使わない）。敵・葉・足場のコスト、葉だけ壊してよい
- 原木へは `GoalLookAtBlock`（reach 4.5）。空中では掘らない（着地を待つ）
- 掘った・倒した後のドロップは、拾えるまで待って拾う。届かないドロップは以後出さない
- レシピ本でのクラフト（100ms 間隔）。棒を持った直後の剣のように、レシピの解放を待つ。解放されていないときは `blocked` に出す
- 設置は 200ms 間隔で、スロットの更新を待つ
- ベッドは `home.inside` からドアと反対向きに置く。就寝は次の時刻更新で夜明けを確かめる
- `enterHome` / `leaveHome` / `dangerOutside`。家の中から外の対象へ向かう行動は、先に家を出る
- 家の中で待つときはドアを向いて静止し、ときどき横を見る
- 被弾で中断（`attack` と `flee` は中断しない）。動詞ごとの時間上限は、Python の HTTP タイムアウト（60秒）より短く
- 建設地の探索（`findSite`、失敗した場所の近くでは探さない）。探索（explore）は進めなかったら失敗を返す
- 家（設計図の範囲）のブロックは、採掘の対象にしない。作業台を設計図の範囲に置かない

M3 以降で足すもの: かまど（入れる・取り出す）、チェスト、弓、ボートなど。仕組みが新しいものは、根源的な行動の追加としてコードで足す（§8）。

**なくすもの**: collect_log, craft_planks, craft_crafting_table, place_crafting_table, craft_door, craft_sword, hunt_animal, hunt_sheep, craft_bed, place_bed, sleep, go_home, stay_inside, build_step, explore, pickup_drop, attack_hostile, flee_hostile, equip_weapon, eat の複合アクション。開発中なので互換は残さない。

## 5. 目標の語彙

Gemini は目標を次の述語とその引数で出す。コードが観測から毎ステップ判定する（LLM の自己申告では達成にしない）。

| 述語 | 例 | 判定 |
|---|---|---|
| `have(item, n)` | `have(bed, 1)`（グループも可: planks, log, door, bed, wool, food） | 持ち物 |
| `built()` | 家の設計図 | 設計図のブロックがすべてワールドにある |
| `placed(bed, home)` | 家の中にベッド | ワールドのブロック |
| `at_home()` | 家の中でドアが閉まっている（壁に穴もない） | 位置とドアと壁 |
| `through_night()` | 夜を越した | 夜を見たあと、時刻が昼に戻った |
| `explored(distance)` | 64m | 開始点からの距離 |
| `cleared()` | ドアの近くで待ち構える敵を片付ける（昼だけ） | ドアから 8m 以内に敵がいない |

`cleared` は frun1 で足した。朝にドアの近くの日陰にスケルトンが残り、安全の制約（§7）で外に出る候補がすべて消えて、ゴールを変えても「家の中で待つ」しか選べなかった。夜は出せない（暗いうちは敵が湧き続ける。ブリッジが理由つきで拒否する）。

M1 の Goal（gather_wood, craft, build_shelter, survive_night, get_food, make_bed, explore）は、この語彙の組み合わせで表せる。例えば make_bed は `placed(white_bed, home)` になる。家の建築は `built(plan)` で、設計図の各ブロックが `placed` の小目標になる。

## 6. 依存関係のソルバー

`have(item, n)` などの述語を、まだ満たしていない小目標の木に分解し、今すぐ進められる末端を返す。

1. 持ち物で足りていれば満たしている
2. 手に入れ方を選ぶ（候補が複数あれば、材料が手元・近くにあるものを優先する）
   - **クラフト**: `minecraft-data` の `recipes`。材料ごとに `have` の小目標を作る。3x3 のレシピは「作業台に手が届く」を小目標に足し、それは `placed(crafting_table, 近く)` か既存の作業台への `goto` で満たす
   - **採掘**: ブロックのドロップ。必要な道具（`harvestTools`）があれば `have(道具)` を小目標に足す
   - **モブのドロップ**: `entityLoot`
   - **製錬**: `minecraft-data` にないので、小さな表を持つ（M3）
3. 材料の種類の違い（板材は8種類の原木のどれからでも作れる）は、レシピが種類ごとに列挙されているので、手元と近くにある種類を選ぶ

**データの欠けと誤り**（補正表を持つ。ここが新しい C の温床なので、テストで押さえる）:
- 羊のドロップに羊毛がない（色がメタデータで決まるため） → `sheep → <色>_wool` を足す
- `blockLoot` は条件を無視した確率になっている（例: 葉のリンゴと棒が `dropChance: 1`。実際はリンゴ約 0.5%）。採掘で手に入る「確実な」入手元は、ブロック自身がドロップする場合と補正表にあるものに限る
- かまどのレシピがない

## 7. 候補の列挙と安全の制約

毎ステップ、ブリッジは次の候補を出す（上限 30 個程度。同じ種類の対象は近い順に数個まで）。

- ソルバーの末端を進める行動（例: 「近くの oak_log を掘る」×3、「板材を作る」）
- 欲求に関わる行動: 食べ物があれば `eat`、脅威があれば `attack` / `flee`
- `wait`

**安全の制約**（コードで候補から外す。Jev には選ばせない）:
- 夜（と、ドアの前に敵がいるとき）に家の中にいるなら、外に出る行動を出さない
- 反射が動いている間は、行動を受け付けない（M1 のまま）
- 戦っている間に体力が 8 以下になったら戦いをやめる（逃げるのは続ける）。そのとき外にいれば、目標に関係なく「家に帰る」を出す

**外した候補は理由として返す**: 安全の制約で候補を外したら、何件をなぜ外したかを目標の `blocked` に入れる。Gemini はこれを「進められない理由」として見る。frun1 では理由が見えず、Gemini は目標を小さくする（剣 → 原木 3 → 原木 1）ことしかできなかった。

**昼にドアの前に敵がいるときの出方**（どれを選ぶかは Jev。Gemini は `cleared` で戦う方針を出せる）:
- `cleared` の末端として、ドアの前の敵への `attack`。素手でも出す。クリーパーは近くで爆発するので出さない（`blocked` に理由）。この候補だけは、ドアの前に敵がいても家を出る
- 壁に出口を掘る（`exit_wall`）: 敵から遠い側の壁を 2 ブロック掘って外に出て、すぐに塞ぐ。掘ったブロックは先に記録し（`home.breach`）、塞げなかった穴は「壁の穴を塞ぐ」候補と欲求になる。穴がある間は家の中でも安全とみなさない
- 家の中で待つ（時間で何かが変わるときだけ。下記）

**待機は目的があるときだけ出す**: 待つと時間が変える事実があるときに、その目的つきで出す。
- 夜・夕方・明け方: 「朝まで待つ」
- 体力が満タンでなく満腹度 18 以上: 「回復を待つ」（自然回復）
- ドアの前の敵が日なたで燃える種類（ゾンビ、スケルトンなど。ハスクは燃えない）: 「燃えるのを待つ」
- ほかに何もできないとき: 「待つ」

目的のない待機をいつも出していたときは、何も変わらない状況でも Jev は待ち続けた（昼に 9 回連続、体力満タンでハスク 2 体のとき 6/6 回）。目的つきにすると、体力満タンでは出口か攻撃を選び、傷を負っているときは回復を待った（下の表）。

| 場面（ハスク 2 体がドアの前、素手） | 候補 | Jev の選択（6 回） |
|---|---|---|
| `have(log)`、体力 20 | 出口 4 | 北の出口 6/6 |
| `cleared`、体力 20 | 攻撃 2 | 攻撃 6/6 |
| `cleared`、体力 16 | 攻撃 2、回復を待つ | 回復を待つ 6/6 |
| `have(log)`、体力 16 | 出口 4、回復を待つ | 回復を待つ 6/6 |

Jev に渡す状態:
- 目標と、小目標の進み具合（例: `have 3 white_wool (1/3)`）
- 欲求: 体力が危険、空腹、夜が近い、脅威と距離（数値と重さだけ。行動の名前は書かない）
- 自分の状態、持ち物、周り

候補の説明に「この候補はどの小目標を進めるか」は書かない（スパイクで悪化した）。

## 9. 移行の順番

1. ソルバーと補正表（ブリッジ）。ワールドなしで動くので、Node のテスト（`node --test`）を初めて入れる
2. 根源的な行動と候補の列挙。`/observe` に候補（動詞と引数）を返し、`/act` で動詞と引数を受ける。M1 の仕組み（家、反射、ドア、クラフト）は中身として使う
3. Python: `GoalType` の閉じた集合を §5 の述語に置き換え、判定はブリッジの結果を使う（§3）。欲求を Jev の状態に入れる
4. 実機での確認: 何もない状態から「家を建てる → 夜を越す → ベッドを置く」を、複合アクションなしで通す（M1 と同じ完了条件）
5. 06・10・09 を更新する

**測ること**: 1手が小さくなるので、Jev の呼び出しが増える（run6 の家は 47 ステップだったが、設置だけで 69 回、それに掘る・拾う・クラフトが加わる）。遅延は約 0.2 秒で問題ないが、1回あたりの費用はまだ分からない。実機で、呼び出し回数と費用、規則との成績の差を記録する

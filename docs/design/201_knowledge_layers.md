## 4. 置き場所の決め方（交通整理）

新しい知識が出たら、次の順に当てはめる。

1. **ゲームの仕様か、事実か**（鉱石の高さ、レシピ、洞窟の鉱石を取らない理由）→ A。手引き（`guides/`）か決まり。ブリッジの定数は、理由を手引きにも書く。
2. **道具や機能の使い方か** → A。`abilities.yaml`（`search_abilities`）。
3. **手順か、準備か**（採掘場の前に予備を作る、松明の数）→ A。手引き。計画（U3）が読めるようにする。
4. **今の世界の状態か**（場所、施設）→ B。
5. **したこと・することか** → C。
6. **やってみて分かった経験則か** → D。教訓。事実と合うか確かめてから、確かでなければ書かない。
7. **誰が何を言ったか** → E。
8. **分析のため** → F。

重複は A に一本化する。同じ内容が A と D にあるときは A を正とし、D の該当は消す。D から A へは「昇格」（§8）で上げる。

## 6. 弱点（観測したもの）

1. **A と D の間に昇格の道がない**。事実が A にも D にも半端に散る。
2. **A の手引きが空に近い**（1 件、約 3700 ステップで 7 回）。経験則の教訓が、A に置くべき手順を担っている。
3. **ブリッジの規則が LLM に見えない**。拒否の文から推測して、因果の違う教訓を書く。
4. **D の書き込みに事実チェックがない**。実績が付くまで残り、悪い教訓が「思い出したこと」として出続ける。
5. **重複**。教訓どうしの言い換え（L1827 と L1828、L1829 と L1830、L1832 と L1818）、A と D の両方。教訓帳は 189 件で上限 200 に近い。
6. **計画（U3）が知識を引く入り口を持たない**。直前の小目標の教訓がたまたま入るだけ。
7. **人が直す入口がない**（U12）。配信中に `lessons.json` を直接編集すると、配信のメモリ上の教訓帳が書き戻す。
8. **寿命**。教訓はワールドを作り直しても残るが、場所に依存するものがある。
9. **孤立**: `data/moves.json` と、実装のない `mcp.memory` の設定（CLAUDE.md の「MCP: memory management」も実態と合わない）。

## 7. 決めたこと

- 層は §3 の A〜F。切り方は「確かか確かでないか」と「誰が書くか」。
- 方針（user、2026-10-20）: ブリッジの修正は可能な限り避け、ハーネス（Python 側）で解決する。したがって、ブリッジの規則を LLM に見せるのは手引きと決まりの文で行い、ブリッジのコードは変えない。
- 置き場所の決め方は §4。
- 実装は §8 のとおり（2026-10-20）。

## 8. やったこと（2026-10-20。ハーネスのみ。ブリッジは変えていない）

1. **手引きを育てる**（A）: 設計書 192 の追補。鉱石の高さ（バイオーム無関係）、この世界の採掘場の決まり、入る前の準備、鉄とダイヤの順。`make_mine` の説明に使いまわし。手引きの先頭に「計画のための要点」の節（下の 3）。
2. **新しい教訓の確認**（D）: `lesson_check.py` の `LessonChecker`。教訓を書いたあと、裏で（書く側は待たない）1 回の LLM 呼び出しで、手引きの本文（確かな知識）と同じ目標の近い教訓を見せて、`wrong`（手引きか仕組みにはっきり反する → 消す）、`duplicate`（既存と同じ助言 → 既存に重ねる。実績を足す）、`ok` を答えさせる。迷うときは ok。確認できなかったとき（LLM のエラー）は残す。結果は `logs/lessons` に `moment: check` で残る。設定 `minecraft.agent.lesson_check`（既定 true）、用途 `lesson_check`（thinking low）。決まりと手引きは、プロンプトの固定の先頭（`CACHE_BREAK` の前）に置き、変わる教訓はそのあとに置く（手引きを直したときだけ先頭が変わるので、キャッシュに乗る）。最初はシステム指示に置いていたが、道具を渡さない呼び出しではシステム指示にキャッシュの印が付かず、実測の読みが 0% だった（`openai_compat_text_generator` の `_messages`: 印は `CACHE_BREAK` の手前と、道具つきのシステム指示だけ）。目標のキーがない教訓（L1832 の形）は、どの目標の教訓とも重ねられる。
3. **計画が手引きを引く**（U3）: 手引きの「計画のための要点」の節（`## 計画のための要点`、次の `## ` まで）を、`planning_notes()` で名前つきの 1 つの文にして、計画のプロンプト（`PLAN_TEMPLATE`）の**キャッシュの境目より前**（固定の部分）に入れる。`read_guide` は道具選びのループの道具で、計画は JSON 一発の呼び出しなので、本文（の要点）を直接入れるしかない。実機の LLM（Haiku）で試すと、要点なしは `have(stone_pickaxe, 1)`、要点ありは「予備を含めて石のつるはし 3 本」の中目標が足された（1 回ずつの試行）。小目標の決定のシステム文（9871/9900 字）には入れていない。
4. **昇格の手順**（D → A）: `tools/lesson_promotion.py`。効いた教訓（`proven`）を、手引きの行に文が似ているもの（「済み?」）と分けて一覧にする。読むだけ。ユーザーが見て、書くものを手引きに取り込む。
5. **重複の整理**: 新しい教訓は 2 で重なる。既存の言い換え（L1827 と L1828 など）は、上限（200）を超えたときの統合（`compact`、設計書 144）に任せる。`_same`（文の近さ + 目標が同じ）が見逃した原因は、言い回しが違うこと（目標のキーは同じだった）。
6. **人が直す入口**: 管理ページ（`/admin`）の「教訓帳」。一覧（新しい順、絞り込み）、消す、足す。`LessonBook.remove()` が保存まで通す。配信を止めずに直せる。足した教訓の出どころは `OPERATOR_SOURCE`（`viewer:運営`、画面では「運営さんに教わった」）で、**LLM の確認（2）は通さない**（人の判断が最終）。
7. **寿命**（(b) に決定し、「試して効かなかったもの」に絞った。2026-10-20、ユーザー）: 世界を作り直すとき（`reset_world.sh`）、**失敗から書いて、思い出したのに一度も効かなかった教訓**（`source == failure` かつ `used > 0` かつ `helped == 0`）を、`data/lessons-unproven-日付.json` に取り分け、作業用の教訓帳から外す（`tools/set_aside_lessons.py`）。視聴者・運営に教わったもの、一度でも効いたもの、まだ一度も思い出していないものは残す。消さないので、戻せる（中身を `data/lessons.json` の `lessons` に足す）。場所や地形の名前を含む教訓が、新しい世界で誤って効くのを避けるため。絞った理由: 最初は `helped == 0` だけで 196 件中 143 件（73%）が当てはまり、うち 94 件は一度も思い出されていなかった（試す機会がなかっただけで、間違いとは言えない）。今の教訓帳では 49 件が当てはまる。選ばなかった案: (a) 全部残す、(c) 「世界に依存する」印を書かせる（書き込みが重くなる）
8. **片づけ**: `data/moves.json` を `data/moves-20261020.json` に改名（設計書 52 の改名前の残り）。実装のない `mcp:` の設定（`MCPSettings`、`MemorySettings`、`config/default.yaml` の `mcp:`）と、CLAUDE.md・feature_reference の「MCP: memory management」を外した。

A 層（手引き、`abilities.yaml`、固定の文）の重なりと食い違い: 石炭と枝の長さは、手引きの一般論の表とこの世界の節で数字が違っていた（石炭 y 43〜96 と y 32、枝 15〜30 と 10）。一般論と世界の決まりを並べて書いたもので誤りではないが、表に「この世界では…（§6）」を足した。残りは一本化が要る（要判断）: 松明の間隔（手引き 6〜8 マスおき、`abilities.yaml` は階段 6 段・坑道 6 マス・枝 5 マス目）、毎回新しく掘る技と使いまわしの決まり、地表から下りる深さの文（`GOAL_SYSTEM_TEMPLATE` は深さの上限なし、手引きは 10 マス以上）、ダイヤの高さ（`FACILITY_TEMPLATE` は y 0 より下、手引きは -58 付近）、苗木・種の 1/4 ルールが 4 か所、定石の順の文（`GOAL_SYSTEM_TEMPLATE` は寝床→食料→建材→資材で、設定の 8 段と違う）。

教訓と手引きの食い違いは、チェッカーで全件（195 件）を手引きに照らすと、はっきり誤りのものは 1 件（L1683「作業台は床に直接置けない」。使われていなかった）だけで、削除した。L1844 のように向きが少し違うものは、矛盾とは判定されなかった（食い違いと言ったのは言い過ぎだった）。

### 10.1 一本化（2026-10-20、ユーザー指示「一本化はどんどんやって」）

ブリッジの定数を正にして、重なり・食い違いを 1 か所に寄せた。
- 松明の間隔: 正は手引きの「暗さ」（ブリッジ `MINE_TORCH` と同じ。階段 6 段・坑道 6 マス・枝 5 マス目）。`abilities.yaml` の `make_mine` からは数字を外した（`dig_mine` が自動で置く。LLM に要るのは本数だけ）。手引きの「幹は 6〜8 マスおき」はブリッジの値と違っていたので直した
- 松明の作り方: 正は `abilities.yaml` の `light_up`。`make_mine` の重複は参照にした
- 鉱石の高さ: `FACILITY_TEMPLATE` の「ダイヤは y 0 より下、石炭・銅は浅い所」を、ブリッジの `ORE_Y` と手引きの表（ダイヤ -58、石炭・銅 32）に合わせた
- 定石の順: `GOAL_SYSTEM_TEMPLATE` の「寝床 → 食料 → 建材 → 資材…」は、設定の 8 段と違っていた（古くなる要約）。状況の「定石」の行を正にして、要約を外した

一本化しなかったもの（理由つき）:
- 苗木・種の 1/4 ルール（`GOAL_SYSTEM`、`abilities.yaml` ×2、設定の理由 ×2）: 読まれる場面が別で、同じプロンプトの中の重複ではない。計画のプロンプトは目標の「理由」（設定）でしか知らず、道具選びは `abilities.yaml` を引く。一つに寄せると、計画か道具選びがルールを失う
- 地表から下りる深さ（`GOAL_SYSTEM` は深さの上限なし、手引きは 10 マス以上）: 別の話だった。前者は階段で下りる深さ（`dig_depth`）、後者は家があるときに石を掘ってよい深さ（ブリッジが断る）
- メモの規則: `Notebook`（3 日寿命）と raw の `NoteBook`（寿命なし）は別の実装

# 83 再現できる課題での測定（ベンチマーク）

2026-10-02、状態: 実装済み、**実機で全 9 回を走らせた**（§7.2。成功の検出・上限での打ち切り・後片づけまで通った）。素手の `house` は 3 回とも 15 分で終わらず、材料を渡す `build` に置き換えた（§7.4）。

## 1. きっかけ

設計書 82 §6 の続き。ログの集計（82）は観察で、世界も目標も毎回違うので「変更が効いたか」を言えない。同じ課題を同じ地形で繰り返し、成否をブリッジが判定する測定が要る。user の答え: 課題は食料 8 個・石のツルハシ・家、素手から、1 課題 3 回、1 回 15 分（「おすすめ通りで良いです」）。

## 2. 何が測れるか

| 課題 | 条件 | 選んだ理由 |
|---|---|---|
| `food` | `have(food, 8)` | 集計で最も行き詰まりやすい種類 |
| `pickaxe` | `have(stone_pickaxe, 1)` | 木 → 道具 → 石の基本の手順 |
| `build` | `built()`（家）、材料つき | ほとんど達成できていない種類。素手では 15 分で建たなかったので、板材・原木・扉を渡して建築だけを測る（§7.4） |

成功 = 上限（15 分）までに条件がブリッジの `/check` で満たされた。上限までに満たされなければ失敗（`timeout`）。1 課題ごとに、成功の回数・成功までの秒の中央値・ステップ数の中央値・死亡の合計を出す。

## 3. 配信と混ざらない作り

配信が動いている間も `ailoveshen-minecraft`（25565）、ブリッジ（3000）、`data/`、`logs/` を使っている。ベンチマークはそのどれにも触れない:

- **サーバー**: `docker/docker-compose.bench.yml`（プロジェクト名 `ailoveshen-bench`、コンテナ `ailoveshen-bench`、ポート 25566、専用のボリューム）。1 回ごとに `down -v` してから `up` するので、毎回新しいワールド（シードは `.env` の `MC_SEED`、`--seed` で変える。同じシード = 同じ地形）。RCON は公開せず `docker exec … rcon-cli` で使う
- **ブリッジ**: 1 回ごとに別のプロセスで起動（ポート 3001、ミラー 25579）。`state.json` は `STATE_FILE`（`home.mjs` の `DATA_FILE`。ほかの保存先 `SKILLS_DIR` / `WORLDMAP_DIR` と同じ流儀の環境変数を足した）、ログは `BRIDGE_LOG_FILE` などで 1 回ごとのディレクトリへ
- **Python**: 1 回ごとに別のプロセス（`tools/benchmark.py play`）。`isolate` が `MinecraftSettings` の `*_path` と `*record_dir` をすべて 1 回ごとのディレクトリに付け替える（入れ子の欄は `watch_record_dir` のように名前をつけて衝突させない）。ブリッジのポートが期待と違えば（配信の 3000 に繋ぎそうなら）始めない
- **ログ**: `play` は loguru のファイルの出力先を作らない（`setup_logging` を呼ぶのは配信の入口 `stream.py` だけ）ので、配信のログ `data/logs/ailoveshen-dev.log` にも `tools/gemini_usage.py` の集計にも混ざらない。出力は 1 回ごとの `play.log`
- **プレイの設定**は配信と同じ（`default.yaml` + `development.yaml` + `.env`）。変えるのは、定石を空にすること、大目標を課題 1 つにすること（教訓・覚えた候補・メモ・小目標の保存も空から）、保存先と記録先、ブリッジのポートだけ

## 4. 走らせ方

`tools/benchmark.py run`（`mise run bench`）。**配信とブリッジを止めてから**: ローカルの LLM（:1919）を共有すると時間の測定が意味をなさず、ブリッジのポートも取り合う。動いていれば、ポートが使われていれば断る（`--allow-stream` で外せる）。

1 回ごと: 新しいワールドでサーバーを起動（"Done" を待つ、最長 300 秒）→ 昼固定の RCON → ブリッジを起動（観測が返るまで）→ `play`（別プロセス）→ 後片づけ（ブリッジを止める、サーバーを `down -v`）。後片づけは失敗しても行う。

`play` は `game.play(keep_going=True)`（配信と同じに、失敗しても待って続ける）を、5 秒ごとに `/check` を聞く監視と並べて走らせる。条件が満たされた時点で成功（時刻を記録）、上限で打ち切り。終わりに `observe` で死亡の数を取る。

**視点を見るには `127.0.0.1:25579`**（ブリッジの視点ミラー。配信の 25578 のベンチ版で、見るだけ）に繋ぐ。**25566（サーバー本体）に繋いではいけない**: 別のプレイヤーとして入って操作でき、ボットの成績にも、モブの湧きにも混ざる。繋いだ回は無効にして撮り直す。

## 5. 結果の読み方

- `seconds_to_success`: プレイの始まりから。`seconds_to_success_after_design`: 家の設計（`purpose=house` の LLM の待ち。`StartPlayUseCase` は家がなければ必ず設計する）を除いたもの。課題そのものに使った時間は後者。`design_seconds` も出す
- `error`（サーバーが上がらない、ブリッジが落ちた、プレイが途中で終わった、終わりにブリッジが答えない）は環境の不具合で、成功率に数えない。数だけ `環境の不具合` の列に出す
- `report` は版（commit と未コミットの変更の指紋。設計書 82 の `logs/runs` と同じ）を出す。`compare 前 後` は同じ課題を並べる
- 各回のディレクトリに、設計書 82 の `goal_ends` / `steps` などがそのまま残る（小目標ごとの内訳が見える）

大目標が課題 1 つなのは**始まりだけ**で、強制はしない。Gemini は目標の決定で大目標を足したり並べ替えたりでき（効率優先の決まり）、結果には課題そのものの腕に加えて、その優先づけも入る。測りたいのはそれも含めた振る舞いなので、そのままにした。

**3 回では差は目安にとどまる。** 成功の回数（例 1/3 → 3/3）と、実行ごとの値を見る。ローカル LLM は非決定で、同じ版でも揺れる。差が小さければ、同じ版を 2 バッチ走らせて揺れの大きさを先に見る。

## 10. 改善サイクルの記録

1 回の流れ: 記録から時間と失敗の出どころを集計する → 原因が確かな欠陥を 1 つ直す → 同じ課題を同じ回数走らせる → **仕組みの数字**（直したはずの失敗が消えたか）と成否・秒の両方で見る。3 回では成否は揺れに埋もれるので、**成否は参考、仕組みの数字を主にする**。比べるときは `compare 前.jsonl 後.jsonl`。

### サイクル 1（2026-10-02、`do_suggestion` の id の `_` と空白）

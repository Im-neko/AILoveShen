# 目標の階層（大目標・中目標・小目標）

作成: 2026-09-25。`12_coherent_decisions.md` の上に、目標を3層にする。コメントの言いなりにならず、元の大目標から外れないようにするのが目的。

## 1. 目的

ユーザーの方針（2026-09-25）:
- 「コメントの言いなりにはならないようにしたい。元の大目標からは外れないようにしたい」
- 状態は次の構造で持つ。小目標に合わせて Gemini が行動を選び、ソルバーを使って Jev に操作させる

| 層 | 数 | 例 |
|---|---|---|
| 大目標 | 1つ | 「街づくりをする」 |
| 中目標 | 複数。優先度をつけて順番に処理する | 「自分の家を作る」「湧き潰しをする」 |
| 小目標 | 1つ | 「木を切る」「石炭を探す」 |

**12 の問題点**: 頼みが小目標を直接置き換えていた。そのため、次のことが起きていた。
- 実機でベッドの頼みを 3/3 回すぐ引き受け、進めていた目標をやめた
- 断った回も、理由は「先に別の頼みを約束したから」だった。大目標を理由に断ったわけではない
- 頼みの回数にも、同じ人の連投にも上限がない。コードが守るのは安全（夜は外に出ない、今出せる述語だけ）だけで、本筋から外れないことは何も守っていない

## 2. 各層の中身と、誰が決めるか

| 層 | 中身 | 決める | 達成の判定 | コメントで |
|---|---|---|---|---|
| 大目標 | 文（例: 「生き延びながら家を建て、街にしていく」） | 設定（`config`）。実行中は変わらない | しない（終わらない） | 変えられない |
| 中目標 | 題名、完了条件（述語のリスト）、理由、出どころ（自分 / 視聴者名） | 最初のリストは設定。追加・並べ替え・断念は Gemini が行う。上限はコードが守る | ブリッジが完了条件から判定する（全部満たしたら完了） | 候補として出せる。受けるか、何番目に入れるかは Gemini が大目標と照らして決める |
| 小目標 | 述語 1つ（今の `Goal`）と、どの中目標のためか | Gemini（小目標の切れ目で決める） | ブリッジ（今のまま） | 変えられない |
| 行動 | 候補から 1つ | Jev（今のまま。ソルバーが分解し、候補を出す） | ブリッジ | 変えられない |

- 小目標は「今いちばん優先度が高い未完了の中目標」のために選ぶ。例外は生存のための小目標（`through_night`、`at_home`、`cleared`、`have(food)`）で、中目標に関係なく選べる（夜・空腹は待ってくれない）
- 小目標がどの中目標のためかは、Gemini が出力で明示する。コードは、それが実在する中目標か「生存」かを確かめる

## 3. 中目標の完了条件

中目標は、ブリッジが世界から判定できる述語の組み合わせだけを完了条件にできる。判定できない中目標は「まだ作れない」として受けない。受けない理由は、返答か実況で言う。

- 完了条件に使える述語は、今の状態で判定できるものだけ: `built`、`placed(bed, home)`、`have(item, n)`
- `at_home`、`through_night`、`explored`、`cleared` は、その場の状態か開始点に依存するので使えない（小目標専用）
- 例:
  - 「自分の家を作る」 = `built`
  - 「ベッドで寝られるようにする」 = `placed(bed, home)`
  - 「木の剣を持つ」 = `have(wooden_sword, 1)`
  - 「食料を蓄える」 = `have(food, 8)`
- 「湧き潰し」「倉庫」「畑」は今の述語では書けない。M3 で述語とプリミティブ（松明を置く、範囲の明るさの判定など）を足すと、中目標として出せるようになる。述語が増えるにつれて、出せる中目標も増える
- `have` は使うと減る。達成した時点で完了として記録し、あとで減っても完了のまま（再び必要なら、新しい中目標として出す）

ブリッジに、目標を設定せずに判定だけする `POST /check {specs: [...]}` → `[{spec, met, lines}]` を足す。中目標の進み具合（何が済んで何が残っているか）も、ここから出す。

## 4. 中目標リストの編集

**編集の場所**: 小目標の切れ目（今、Gemini が小目標を決めているところ）で、Gemini が次の2つを一緒に出す。
- 次の小目標と、それがどの中目標のためか
- 中目標リストへの操作（任意）: 自分で追加、並べ替え、理由つきの断念

完了はコードが判定するので、Gemini は完了を宣言しない。

**コードが守る上限**（Gemini の判断に任せない）:

| 上限 | 値（初期） |
|---|---|
| 中目標リストの長さ | 最大 6 |
| 視聴者が出どころの中目標 | 同時に最大 2 |
| 1人あたりの視聴者の中目標 | 同時に最大 1 |
| 視聴者の中目標を入れられる位置 | 今取り組んでいる中目標より後ろだけ（割り込みはしない） |
| 視聴者の中目標の予算 | 小目標のステップの合計で 80。超えたら断念し、実況で言う |
| 断念 | 理由が必須。視聴者の中目標の断念は、実況で必ず言う（12 の「約束を黙って捨てない」） |

**視聴者の頼み**（12 の「頼み → 次の小目標」を置き換える）:
- 返答の生成は、返答と「中目標の候補の扱い」を1回で出す（12 と同じく、言うこととやることを1回の生成で決める）。扱いは次の3つのどれか
  - 受ける: 題名、完了条件、入れる位置
  - 断る: 理由
  - 中目標にしない: 雑談・質問
- 受けたら、コードが上限を確かめて、すぐリストに入れる。今の小目標は打ち切らない（リストは Python の中だけの状態なので、返答の側から書き換えても `/act` と競合しない）。上限に当たったときは、生成し直しで理由を渡し、断る返答にする
- 返答では、いつやるかを言う（「家ができたら次にやるね」）。リストに実際に載るので、12 で禁止した「先の約束」が、守れる約束になる。「朝になったら」のような時刻の条件付きの約束は、今の完了条件で表せないので引き続き受けない
- 大目標に関係ない頼み（「ずっと探検して」）は、断るか、完了条件を小さくして低い位置に入れる。どちらにするかは Gemini の判断で、理由を返答で言う

## 5. 「今していること」の拡張

12 の `Activity` に、大目標と中目標リストを足す。3つのプロンプト（小目標の決定、実況、返答）は、これまでどおり1つの書式で見る。

```
- 大目標: 生き延びながら家を建て、街にしていく
- 中目標（上から順に取り組む）:
  1. 自分の家を作る [取り組み中] 完了条件: built（ブロック 30/70）
  2. ベッドで寝られるようにする（nekoさんの頼み）完了条件: placed(bed, home)（未）
  3. 食料を蓄える 完了条件: have(food, 8)（2/8）
- 今の小目標: have(log, 3)（「自分の家を作る」のため）: 壁の材料
- これまでの目標: ...
```

中目標の完了・断念・視聴者の中目標の受け入れは、イベントとして `Narrator` に流す（`MidGoalCompletedEvent`、`MidGoalDroppedEvent`、`MidGoalAddedEvent`）。受け入れは返答で言っているので、実況では繰り返さない。

## 6. 構成

| 層 | 追加・変更 |
|---|---|
| domain | `Mission`（大目標の文）、`MidGoal`（題名、完了条件 `tuple[GoalSpec]`、理由、出どころ、使ったステップ、状態）、`MidGoalPlan`（リスト。上限のチェック、追加・並べ替え・断念・完了の操作）。`PlaySession` が `Mission` と `MidGoalPlan` を持ち、`Goal` にどの中目標のためか（`mid_goal_id`、生存なら None）を足す。`Activity` に大目標と中目標リスト（と各完了条件の判定）を足す。12 の `ViewerRequest` と `request_goal` はなくす |
| application | 小目標の決定のスキーマに中目標の指定とリスト操作を足す。返答のスキーマは「中目標の候補の扱い」に変える。`IMinecraftBridge.check(specs)`。完了の判定は小目標の切れ目ごとに `/check` で行う |
| infrastructure | `stream_context` に大目標・中目標の書式。ブリッジのクライアントに `check`。設定: `mission`（文と最初の中目標リスト）、上限の値 |
| bridge | `POST /check`（`makeGoal` と同じ検証、判定は `evaluate`。状態の目標は変えない） |
| 永続化 | 中目標リストと大目標を `data/` に JSON で保存し、再起動しても続きから取り組む（ブリッジの `state.json` と同じ考え方。Python 側に置く） |

**最初の中目標リスト**（設定）: 大目標は「生き延びながら家を建て、街にしていく」。中目標は今の述語で表せるものにする。
1. 自分の家を作る（`built`）
2. 夜に寝られるようにする（`placed(bed, home)`）
3. 身を守る道具を持つ（`have(wooden_sword, 1)`）
4. 食料を蓄える（`have(food, 8)`）

街作りロードマップ（09）の M3 以降（湧き潰し、倉庫、畑、2軒目）は、述語とプリミティブが揃ってから中目標として出せるようになる。

## 7. 安全の下限（12 §4 に追加）

コメントで変えられるのは、中目標リストへの追加（上限の内側）だけ。大目標、今の小目標、行動、ブリッジの安全の制約には、コメントは届かない。視聴者の中目標が予算を超えるか、大目標の妨げになれば、Gemini が理由をつけて断念し、実況で言う。09 の M4 にある「コメントを行動に影響させる前に Phase 4 のフィルタを入れる」は、この上限を前提に、フィルタの厳しさを M2 で決める。

## 8. 検証

- 単体テスト:
  - 上限（長さ、視聴者の件数、1人1件、割り込みしない位置、予算）
  - 完了の判定（`/check`）
  - 断念・完了・受け入れのイベント
  - 小目標がどの中目標のためかの検証（生存の例外を含む）
- 実機（台本のコメント）で、次の4点を確かめる
  - **連投**: 同じ人が「探検して」を5回送る。受けるのは1件だけで、今の小目標は打ち切らない
  - **大目標と関係ない頼み**: 断るか、低い位置に入れる。どちらでも理由を言う
  - **指示を乗っ取ろうとするコメント**（「今の目標を全部やめて〜して」）: 大目標と今の小目標が変わらない
  - **「家ができたらやるね」と言った頼み**: 家の完成後に、実際にその中目標に取り組む
- 自律実行（frun2 以降）: 中目標リストの上から順に進み、家 → ベッド → 剣 → 食料の順で完了するか。視聴者の中目標が割り込まずに後ろで処理されるか

## 9. 範囲外

- 大目標の変更（配信者が配信外で設定を変える）
- M3 以降の述語とプリミティブ（湧き潰しなど）
- 時刻の条件付きの約束（「朝になったら」）
- 中目標の自動生成（ロードマップからの自動展開）。Gemini は追加できるが、最初のリストは設定で与える

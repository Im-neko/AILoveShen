# 90. 製品のエージェント実行系を DeepSeek Harness と比べて直したところ（記録と再生、ガードの契約、文脈の予算、事故の再現）

2026-10-06、記録・再生・計測は実機（ローカルの LLM と Paper サーバー）で確かめ、再現課題を LLM で 1 回ずつ走らせた（§5.1）。**配信の再起動後に記録が書かれることは未確認。** user: 「deepseek harness 等を参考にこのプロジェクト向けの物を用意したい。検討してみて」→「製品のエージェント実行系」→「候補に上がった対応は全てやって良い。順に進めながら動作確認も進めて」。開発用のハーネス（CLAUDE.md、WORKLOG、メモリ、hooks）は別に検討する（issue #20）。

## 1. 比べたもの

DeepSeek Harness（`deepseek-ai/deepseek-harness`、MIT）は、モデルは考えるだけで、それ以外（ファイル編集、端末、コンテキスト、計画、サブエージェント）をすべて harness が受け持つ、全部がプラグインのコーディングエージェント。読んだのは `docs/AGENTS.md`、`defensive-patterns.md`、`tool-execution-pipeline.md`、`agent-lifecycle.md`、`testing.md`（`capability-seams.md` は冒頭だけ）。

### 持ち込んだもの（規律）

| DeepSeek Harness | ここでの形 | 節 |
|---|---|---|
| セッションを追記専用のイベントログにし、モデルの応答を再生して回帰テストにする（`llm-replay`、snapshot） | LLM の呼び出しを全文 JSONL に残し、記録した出力を今の検証に通し直す | §2 |
| ツール実行は 1 本の道（pre-execute → 単調なガード → 実行 → 結果）で、ポリシーは道の側にある | `callTool` の関門の順序を契約テストにする | §3 |
| 最初のリクエストの重さ（約 13.5k トークン）を隠さず測り、上限を機械で強制する（`verify-doc-budgets`） | 固定部分の上限テストと、記録からの内訳 | §4 |
| 実機の検証を別の層にする（「行カバレッジは必要で、十分ではない」） | 未確認の一覧と、起きた事故の再現課題 | §5 |
| 状況ごとにツールの集合を変える（preset） | **入れなかった**（§6、記録で上限を測った） | §6 |

### 持ち込まないもの

- 全部がプラグイン（Cordis）: DeepSeek Harness は他人が拡張するための基盤。こちらは 1 人の配信 AI で、得るものがなく費用だけが大きい。
- サブエージェント、ベクトル記憶、MCP のレジストリ、サンドボックス、履歴の圧縮: 課題が違う。呼び出しは履歴を持たない（設計書 21 §2）ので、圧縮する履歴がない。
- 多言語の文書、行カバレッジ 100% のゲーム: 規模が合わない。

## 2. 判断の記録と再生

**問題:** プロンプト全文とモデルの出力は、メモリ上の直近 50 件（`InMemoryGenerationLog`）にしかなく、再起動で消えた。「モデルが不正な出力を出して差し戻した」は最も多い失敗の種類のひとつ（WORKLOG 2026-09-26 以降で約 50 件。見出しと本文を正規表現で数えた概数）なのに、その出力が残っていないので、検証を直しても過去の出力で試せなかった。

**作ったもの:**
- `JsonlGenerationLog`（`infrastructure/adapters/storage/jsonl_generation_log.py`）: 画面に出す直近の分と画像は `InMemoryGenerationLog` に任せ、各呼び出しを `logs/generations/gen-<開始時刻>.jsonl` に 1 行ずつ追記する。`gemini.generation_log_dir`（空ならメモリだけ）、`gemini.generation_log_keep_days`（既定 3 日。開始のときに古いファイルを消す）。書けなくても生成は止めない。画像はファイルに書かない。
- 記録に足した欄: `system`（システム指示）、`tools`（渡した道具の名前。ローカルのアダプターのみ）。ほかに、すでに `model`（`local:<モデル名>` か `gemini:<名前>`）、`purpose`、`prompt`、`output`、`tool_calls`、`tokens`、`elapsed_ms`、`error` がある。
- `tools/replay_decisions.py`: 記録した道具の呼び出し（`tool` / `tool_after_failure` / `tool_stuck`）を `parse_tool_call` に、目標の決定（`goal` / `goal_after_failure`）を `parse_decision` に通し直し、受け入れ・断られた・答えなしを数え、断られた理由を種類ごとにまとめる。`--export` で断られた記録を回帰テストの元として書き出せる。

**できないこと:** 通せるのは状態を要らない検証だけ。ブリッジの状態を見る検証（述語の語彙、`plan_lint`、ブリッジの 400）は世界がないので通せない。世界の再生ではない（設計書 82 §5 のとおり、世界のスナップショットはない）。記録が溜まるほど役に立つ。**今はまだ、実際に断られた出力が 1 件も溜まっていない。**

**ログの量（見積もり。実測は再起動後）:** 記録するプロンプト本文は約 4.3k トークン（約 12KB。道具の定義はプロンプトとは別に送られるので含まれない）に出力と思考が加わる。24 秒に 1 ステップなら 1 日で約 45MB。3 日で消す。プロンプトには視聴者のコメントが入る。`logs/` はコミットされない。

**確かめたこと（2026-10-06）:** 動いているローカルの LLM（`Gemma-4-26B-A4B-NVFP4`）に実際の道具の定義（38 個）で道具の選択を 1 回送り、アダプターが 449 バイトの 1 行を書き、`replay_decisions.py` がそれを受け入れ 1 件と数えた。テストは、偽のサーバーで アダプター → JSONL → 再生 の全部をつなぐもの（`test_replay_decisions.py`）を含む。再生の検証を壊すと 3 件のテストが落ちることも確認した。

**気づいたこと:** ステップの記録（`logs/steps`）の `by: "gemini"` と、実行の記録（`logs/runs`）の `gemini_model` は、実際に答えたモデルを表さない。`.env` の `LOCAL_LLM=1` で、画像のない呼び出しはすべてローカルの LLM が答えている。「gemini」は主のテキスト生成器の古い呼び名。実際のモデルは新しい `gen-*.jsonl` の `model` で分かる。名前は直していない（記録の読み手が多く、直すなら別に決める）。

## 3. ガードの順序の契約

**調べたこと:** 最初は「拒否の判定が散らばっている」と見たが、道具の呼び出しの入口は `tools.mjs` の `callTool` の 1 か所で、順序はすでに決まっていた:

`unknown tool` → 反射（`state.reflex`）→ 実行中（`state.busy`）→ 断られた手の台帳（`demolish: true` だけが通り越す）→ 道具ごとの検査（距離、保護、水を止めているブロック、材料）→ 夜の籠もり（`shelterOf`）→ 実行（`run`）

調べものの道具は、この関門を通らずにすぐ返る。保護（`protectedReason`）と水・溶岩（`liquidReason`）は道具ごとの検査の中にあり、`dig` の `demolish` が保護を通り越すが、水・溶岩は通り越せない。

**作ったもの（挙動は変えていない）:**
- `minecraft-bridge/test/tool-gates.test.mjs`（7 件）: 順序の契約。すべての行動の道具に実行があること（書き忘れると `unknown tool` と断られ続ける）、反射と実行中はどの行動の道具も実行しないこと、反射が実行中より先であること、台帳は `demolish` だけが通り越すこと、調べものは関門に断られず `run` を呼ばないこと。順序を入れ替えると落ちることを確認した。
- `tests/unit/application/test_tool_catalog_bridge.py`（2 件）: Python が見せる道具の一覧（`tool_catalog.py`）とブリッジの一覧（`tools.mjs`）が食い違わないこと（検索の道具と `look_screen` は Python が処理するので除く）。
- `callTool` に順序のコメントとテストへの案内を 1 行足した。

**入れなかったもの:** ブリッジに `uncaughtException` / `unhandledRejection` のハンドラはない（シグナルだけ）。ログ（`logs/bridge.log` ほか）に未処理の例外で落ちた痕跡はなく、100 回の起動はほぼ `npm run dev` の再起動。実害の証拠がないので足していない。Node は未処理の拒否で落ちるのが既定で、ログだけ出して続けるハンドラは壊れた状態のまま動かし続ける（握りつぶし）ことになる。落ちた事例が出たら、原因を調べてから決める。

**測ったこと（2026-10-06）:**

- ルールの文（`TOOL_TEMPLATE` の固定部分）: 推定 1,365。`TOOL_STUCK_SECTION` 740、`TOOL_SKILLS_SECTION` 175。
- 1 ステップの時間は入力のトークン数でほぼ決まる（設計書 51 §2）。

**作ったもの:**
- `tests/unit/infrastructure/adapters/prompts/test_context_budget.py`（3 件）: 定義の推定が 8,800（ふだん）/ 9,450（行き詰まり）、ルールの文 1,450、行き詰まりの節 780、技の節 190 を超えたら落ちる。余裕は約 5%。上限が緩すぎて何も捕まえなくならないよう、実測の 1 割を超える上限も落とす。超えたら、削れるものを削り、それでも要るときだけ上限を上げ、理由をここに書く。20 字ずつ 38 個の説明を足すと落ちることを確認した。
- `tools/prompt_budget.py`: 記録から、用途ごとの実測の入力トークン・時間（中央値、p90、最大）と、`## ` の見出しで割った節ごとの推定の平均を出す。ステップごとに変わる部分（今していること、まわり、直近の道具）はテストでは測れないので、こちらで見る。

**入れなかったもの:** 履歴の圧縮（履歴がない）、キャッシュ（効かないと測った: 設計書 51 §2、`cached=0`）。

## 5. 未確認の一覧と、事故の再現課題

**未確認の一覧:** WORKLOG の 2026-09-26 以降の 233 件のうち、「未確認」が見出しか本文にあるのは 111 件（約半分）。ただし見出しに印があるのは 11 件だけで、残りは「確かめたが、これは未確認」と本文に書いたもの。「約半分が未確認」は上限の数字で、記録の全体が未確認という意味ではない。`tools/unverified.py` が WORKLOG からその一覧を作る（2026-10-06 の全体で 126 件: 全体が未確認 11、本文に残りがある 115。最も古いのは 12 日前）。別の一覧を作らないので、WORKLOG とずれない。実機で確かめたら、見出しの「未確認」を「確認済み（日付）」に書き換える。そうすると一覧から消える。

**事故の再現課題（`config/benchmark.yaml` の `scenarios`）:** 既定の 3 課題（食料・ツルハシ・家。user と合意済みの設定）は変えず、名前で指定したときだけ走る別の欄を足した（`mise run bench -- --tasks night,pond,cage`）。`Task` に `setup`（ボットが入ったあとに行う RCON コマンド。`time` / `weather` / `fill` / `setblock` / `execute` だけ、1 行）と `freeze_day: false`（夜の課題が時間の進みを求める）を足した。プレイヤーがいなければ、状況をつくれず失敗する。

| 課題 | 再現する事故 | 状況 | 条件 |
|---|---|---|---|
| `night` | 家も道具もない夜に死ぬ（設計書 89） | 夕方（`time set 12000`）から、昼固定なし | `have(log, 4)`（昼の仕事のまま夜をどう過ごすか。**見るのは死亡の数**） |
| `pond` | 海にスポーンして水の上で過ごした（設計書 89） | 半径 12・深さ 3 の池の真ん中 | `have(log, 4)`（陸に上がって木に着く） |
| `cage` | 水が入った小部屋に 40 分いて溺れた（設計書 87、88） | 土の殻（3x4x3）の下半分が水。石は素手では何も落ちないので土 | `have(log, 4)`（素手で掘って出て木に着く） |

条件は大目標に使える述語だけ（`Objective` が検査する）。最初は `through_night` と `explored` で書いて、走らせて初めて断られた（`through_night cannot be a condition of an objective`）。ドライランも、`parse_spec` だけを見たテストも通っていた。テストは `Objective` を作るところまで見るように直した。

**確かめたこと（2026-10-06）:** ベンチ用の Paper サーバー（配信とは別）で、3 つの状況づくりを実際に流した。`night`: 時刻が 12083（夕方）。`pond`: ボットが水の中、12 ブロック先に水があり 14 ブロック先にない。`cage`: ボットが水の中、2 ブロック横が石、水面の上に 2 ブロックの空気、天井は石で、ブリッジは `you are swimming in water: you are not on land` と認識した。

### 5.1 LLM で走らせた結果（2026-10-06、各 1 回、1 回 10 分、配信を止めて）

| 課題 | 結果 | 歩数 | 死亡 |
|---|---|---|---|
| `night` | timeout（`through_night` の小目標は 523 秒・46 ステップで成立。そのあと原木に取りかかる前に上限） | 47 | 0 |
| `pond` | **成功 108 秒** | 6 | 0 |
| `cage` | timeout（下記。途中で LLM サーバーが落ちた） | 9 | 0 |

1 回ずつなので傾向でしかない。分かったこと:
- `night`: 家も道具もない夕方でも 0 回死亡。目標の決定 3 件のうち 1 件（`goal_after_failure`）は、大目標に `through_night` を条件にした案を出して、`parse_decision` に断られた（配信では差し戻される）。これは `replay_decisions.py` が実際の記録から見つけた、本物のモデルの誤り。
- `pond`: 設計書 89 の陸に上がる手（`reach_land`）が、水の中から木までの道を通した。
- `cage`（**事故は再現できた**）: 土の壁の中の水の中で、`swim to the nearest land at …` を座標を 1〜3 ブロックずつ変えて 4 回試し（どれも `could not climb onto land`、25〜36 秒かかる。台帳は座標が違うので止められない）、`explore` は `No path`、小目標は 3 回失敗して `have(food)` と `have(log)` を行き来し、掘って出る手を一度も選ばなかった。原因はコードの読み（実行では未確認）: `climb_out`（`candidates.mjs` の閉じた所）は `fillItem`（土か丸石の持ち物）がないと候補に出ず、素手の始まりには出ない。`reach_land` は壁の外の「陸」を壁の高さを見ずに急ぎの手として出す（`grid` は壁を `+4` と示している）。壁を掘る手の候補はなく、道具の `dig` を座標つきで LLM が選ぶしかないが、選ばなかった。user の「ツルハシが無くて困った時は素手で掘っても良い」（設計書 87）は、閉じた所からの脱出には入っていない。
- `cage` は 14:46（UTC）から LLM サーバーが応答せず（`ReadError`、そのあと `ConnectError` 4 回）、終わりの約 3 分が空振りだった。ベンチはこれをタイムアウト（失敗）に数えていたので、**環境の不具合（`error`）に数える**ようにした: 終わりの側で続けて 3 回以上 LLM の呼び出しが失敗していたら（`llm_outage`、記録から数える）。この `cage` は新しい規則なら `error`。**サーバーが戻ったら `cage` をもう一度走らせる。**
- ベンチの `play` も LLM の呼び出しを実行ごとのディレクトリ（`logs/bench/<バッチ>/<課題>-<n>/logs/generations/`）に残すようにした（以前はメモリだけ）。

実記録でツールを動かして見つけた不具合: `replay_decisions.py` が目標の決定をすべて「JSON でない」と断った。ローカルの LLM は JSON をコードの囲み（```json）に入れて返し、配信は `extract_json` で取り出してから検証するのに、ツールは直接 `json.loads` していた。配信と同じ `extract_json` を使うよう直した。

実記録の内訳（`prompt_budget.py`、`night`）: 道具の選択は入力 9.2k トークン・8.2 秒（定義 37 個で約 6.6k、「決まり」の節は推定 1,166 でプロンプト本文の 43%、「配信者が今していること」733）。目標の決定（`goal_after_failure`）は 8.7k〜10.2k トークン・約 10 秒で、「小目標を選び直す理由」の節が本文の約 80%（推定 2,060）。

## 6. 状況別のツール集合を入れなかった理由

DeepSeek Harness の preset（状況ごとに見せる道具を変える）を試す前に、効果の上限を記録で測った。`tools/refusal_report.py` が `logs/steps` の `result` 行を数える（2026-10-06、149 ファイル）:

| 理由の種類 | 件数 | 全結果（12,775 件）に対して |
|---|---|---|
| 材料・食料・道具がない | 729 | 5.7% |
| 距離の間違い・遠すぎ（符号の落とし、など） | 461 | 3.6% |
| 古い対象（もう空気、今の提案にない） | 386 | 3.0% |
| その他 | 314 | 2.5% |
| 反射が対処中 | 291 | 2.3% |
| 呼び方（調べものの上限、形） | 108 | 0.8% |
| 水・閉所 | 100 | 0.8% |
| 台帳（前に断られた手） | 59 | 0.5% |
| 夜の籠もり | 21 | 0.2% |
| **断られた手の合計** | **2,469** | **19.3%** |

夜の籠もりと水・閉所の拒否は合わせて全結果の 1% で、状況で道具を絞って減らせるのは多くても約 1% のステップ。道具の定義は 38 個で約 6.9k トークンなので、仮に 3 割絞っても約 2k トークン、設計書 51 §2 の式（入力 3,100 トークン/秒）で約 0.7 秒、1 ステップ約 24 秒の 3%。一方、拒否の大半は引数の誤り（材料、距離、古い対象）で、道具を絞っても直らない。**入れない。** 拒否の約 20% が 1 手分の時間（約 7〜25 秒）を無駄にしているので、直す先は上の表の上から 3 つ。この集計は、変更の前後で `--since` を使って比べられる。

## 8. 残り

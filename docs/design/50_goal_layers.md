# 目標の 4 層（最終目標・大目標・中目標・小目標）

作成: 2026-09-29。`13_goal_hierarchy.md`（目標の 3 層）と `26_steps_and_context.md`（手順 `plan_steps`）を置き換える。状態: 段階 2（仕組み）は実装済み（§11）、段階 3（改名と語彙）も実装済み（§12）、計画（大目標ごとに LLM が中目標と小目標を前提つきで書く）は §18。

## 1. 目的

ユーザーの依頼（2026-09-29）:
- 大目標は基本的に変わらないので、最終目標にする。代わりに大目標を直近の目指すもの（資材保管庫の建設など）にする
- 中目標を資材の確保や施設の建設などの行動の単位、小目標を「〇〇まで移動」「ベッドで寝る」のような具体的な動作を表すものにしたい
- 決めたこと: 両方（挙動の改善と、配信での分かりやすさ）が動機。大目標は最大 6 個を並べ、入れ替えられる。基盤整備は大目標の 1 つ。視聴者の頼みは大きさで層を分ける

今の問題（13・26 の実装）:
- 中目標のリストに、粒度の違うものが平らに並ぶ（「保管庫を建てる」「丸太を 64 個集める」「農場」）。手順（`plan_steps`）は中目標の内部に隠れ、進み具合・状態・停滞が中目標の単位でしか見えない
- 配信では「今なにをしていて、なぜか」が 1 本で辿れない

## 2. 4 層

| 層 | 型（改名後） | 問い | 完了の形 | 決める | 見直し |
|---|---|---|---|---|---|
| 最終目標 | `Mission`（型名は変えない） | なぜ | 終わらない。設定で決め、配信中は変わらない | 設定 | しない |
| 大目標 | `Objective`（今の `MidGoal`） | 何を成し遂げるか | 成果物が世界にある、または基盤が整っている（`/check`） | Gemini（追加・入れ替え・断念）。最大 6 個 | 進まなければ Gemini が後回しか断念 |
| 中目標 | `Job`（今の `PlannedStep`） | どの仕事で成し遂げるか | 資源・配置・整地などの状態（`/check`）。一度満たしたら済み（ラッチ） | Gemini が大目標ごとに書く | 進まなければ Gemini が書き直す |
| 小目標 | `Goal`（変えない） | 今の 1 回の遠征 | 1 回の遠征で届く状態述語 | Jev（既定）、Gemini | 詰まれば Jev が別の手 |
| （行動） | tool / primitive | 動詞 | 秒 | Jev / Gemini の道具 | 反射 |

- 最終目標は日本語の呼び名だけ変える。コードの `Mission`、設定 `minecraft.mission`、`data/mission.json` の `mission` は変えない（改名の対象を増やさない）。今の設計書・プロンプト・オーバーレイが「大目標」と呼んでいるのは最終目標のことなので、語彙の入れ替えは §9 の 1 回で行う
- 「〇〇まで移動」「ベッドで寝る」は動詞で、行動層（`goto` / `sleep_at`）にある。小目標は状態述語のまま（`at_home`、`through_night`）。オーバーレイに動作の言葉を出すのは、今の日本語 `label` と `intent` が受け持つ
- 「なぜ」のはしご: 小目標は中目標のため、中目標は大目標のため、大目標は最終目標のため。生存の小目標だけは中目標に属さない（13 §2 の例外のまま）

## 3. 大目標

- 種類（`kind`）はコードが条件から決める。Gemini は書かない（弱いモデルの書く項目を増やさない）
  | kind | 条件に使える述語 | 例 |
  |---|---|---|
  | `build` | `built(name)` だけ | 資材保管庫を建てる |
  | `facility` | `facility(name)` だけ | 小麦畑を作る |
  | `infrastructure` | `have` / `placed` / `stored` / `planted` / `farmed` / `leveled` / `lit` / `custom` | 石のツルハシと松明を持つ、食料を蓄える |
- `build` と `facility` の大目標は、資材・整地・内装を条件に書けない（中目標に置く）。混ぜた条件は差し戻す: 「材料は中目標に書く」
- 街の段階（`stage`、`prepares_town`）は大目標の属性のまま。段階の条件は段階の定義が決めるので、`kind` の検査は受けない（混ざった条件は `infrastructure` として扱う）。断念できないのも今と同じ
- 視聴者の頼みは、大きいもの（自分の名前を持つ建物・施設）を大目標として、待ち行列の後ろに入れる（13 §4 のとおり、今取り組んでいるものより後ろ。`when: now` の例外も同じ）。小さいものは §5
- 上限（コードが守る）: 大目標 6 個、視聴者が出どころのもの同時 2 人、1 人 1 件（§5 の中目標と合わせて数える）、予算 80 ステップ。助言（`suggested_by`）は数えない（49）

## 4. 中目標

- 中目標は大目標ごとのリスト（1〜6 個）。条件 1 つ + `together`（44）+ `approach`。id（`j1` …）、状態（`pending` / `done` / `dropped`）、出どころ（配信者 / 視聴者 / 助言）、理由を持つ
- **ラッチ**: `/check` で一度満たしたら `done` のまま（13 §3 の `have` と同じ扱い）。次の手順で材料を使って未達成に戻っても、済みのまま。今は `GoalChooser` が毎回 `/check` で判定し直している
  - `_check_step_order`（後の手順が済んで前が未達成なら差し戻す）は、ラッチした状態で比べる
- **書き直し**: Gemini が出す中目標のリストは「これから残す未達成のもの」。コードは既存のものと同じ条件（`same_as`）を探して id と出どころを引き継ぎ、済み（`done`）と視聴者・助言の中目標は、断念に理由が書かれない限り消さない
- 上限: 大目標ごとに未達成 8 個（Gemini の 6 個 + 視聴者・助言の分）
- 進み具合と停滞
  - 大目標の進み具合: 成果物の大目標は `/check` の数え（ブロック 30/70）、`infrastructure` は済んだ中目標 / 全体（断念を除く）。中目標を足すと分母が増えて戻って見えることがある。書き直しだけでは変わらない（テストで確かめる）
  - 停滞: 中目標が 1 つ済む、または今の中目標の `(n/m)` が変わるとき進んだとする。`mid_goal_stall_steps`（60）を中目標の単位で数える。書き直しは数え直さない
  - 停滞の文言（`MID_STALLED`）の文字列判定（`lessons.py`、`play.py` 3 か所）は同時にそろえる

## 5. 視聴者の頼みの層

返答の `request` に、頼みの層を持たせる。

| 頼み | 層 |
|---|---|
| 自分の名前を持つ建物・施設 | 大目標（`build` / `facility`） |
| 今の大目標の材料・一歩になるもの（「もっと丸太を」） | 今の大目標の中目標（`serves: current`） |
| 今の大目標と関係のない小さなもの（「松明を置いて」） | 小さな `infrastructure` の大目標（後ろに入る） |

- 13 §4 の上限（1 人 1 件、同時 2 人、今のものの後ろ）は、大目標と中目標を合わせて数える。中目標だけ数えないと、同じ人の連投が中目標に際限なく入る（13 §9 の連投の確かめが崩れる）
- 予算 80 ステップは、その頼みの小目標に使ったステップを、中目標なら頼みの中目標に、大目標なら頼みの大目標に数える
- ユーザーの決めた「小さいものは今の大目標の中目標」を、なぜ・はしごに合わせて「今の大目標に関係するものだけ」に絞った。関係のない小さな頼みを中目標にすると、なぜが辿れなくなる。異論があれば戻す

## 6. 小目標の選び方

- Jev（`GoalChooser`）は、今の大目標の未達成の中目標と生存の選択肢から選ぶ（今と同じ形。手順が中目標になる）
- 大目標が入れ替わっても、外れた大目標の中目標は保つ。戻ったときに書き直さない

## 7. 保存とオーバーレイ

- `data/mission.json` は移行しない（リリース前）。保存に `format`（版。今は 2）を持たせ、版が違う・壊れている・今の検査に通らないファイルは、例外にせず設定の初期リストで始める（今の `_load_plan` の、最終目標の文が違うときの経路と同じ）。次の保存で上書きされるので、読めなかったファイルは `mission.json.unreadable` に写して残す。今のファイルは着手前に `data/backups/` にも退避しておく
- `GET /api/goals` とオーバーレイ: 最終目標 → 大目標のリスト（進み具合、視聴者の頼み）→ 今の大目標の中目標（済み・今・待ち）→ 小目標（吹き出し）。`/overlay/vtuber` は 4 層をそれぞれ名前付きのカード（最終目標・大目標・中目標・小目標）で出す（2026-09-29: 中目標は大目標の中の名前のない小さい行で、`compact=1` では消え、見つからなかった。`compact=1` は中目標のカードを出さない）。中目標が済むとトースト
- `Narrator`: 大目標の完了・断念（今の `MidGoal*Event`）に加えて、中目標の完了を次の実況に混ぜる（`JobDoneEvent`）。小さな中目標の完了ごとには話さず、大目標の境目と長い中目標の完了だけ話す（`JobDoneEvent`: `ObjectiveKeeper` が小目標の切れ目の判定で済みにしたときに 1 回だけ出す。`Narrator` は取っておいて次の切れ目に話し、話すかどうかは間合いの判定に任せる。強制的に話すのは大目標の完了・断念だけ。視聴者の手順の断念は、大目標と同じ `ObjectiveDroppedEvent` で必ず言う）

## 11. 段階 2 の実装（2026-09-29）

型名は今のまま（`MidGoal`、`PlannedStep`）。改名は段階 3。この節は段階 2 の時点の名前と語彙で書いてある（今の名前は §12 の対応表）。

| 層 | 実装 |
|---|---|
| domain | `PlannedStep` に `id`（`j1` …）・`state`（`JobState`）・`requested_by` / `suggested_by`・`steps`（視聴者の手順が使った予算）・`progress`・`ended_because`。`MidGoal.kind`（`ObjectiveKind`、`objective_kind(conditions)` が混ぜた条件を `ValueError`）、`open_steps` / `done_steps`。`MidGoalPlan.set_steps`（マージ）、`add_step`、`judge_steps`（ラッチ）、`drop_step`、`viewer_step`、`viewers`、`check_room(job=)`、`charge(id, spec)`、`take_dropped_steps`、`next_step_id` |
| application | `MidGoalKeeper.judge` が一番上の中目標の未達成の手順を判定して済みにし、進み具合を保つ（`_judge_steps`）。`accept` は `proposal.job` なら `_accept_job`（今の手順のすぐ後ろで、先に頼まれた手順の後ろ。`now` は先頭。今の大目標を返す）、`withdraw` は手順も、`step_counted` は予算を超えた視聴者の手順の断念も伝える。`GoalChooser` は未達成の手順から選び、満たした手順は済みにする。`AdvancePlay`: `_check_step_order` は済みの手順を数えない、`_step_status` は済みを判定せず済みのまま見せる、決定の検証で書き直しが 8 個を超えるなら差し戻す、`_MidWatch`（停滞は手順が済む・条件の数が動く・今の手順の数が動くと進んだ。手順を書き直して今の手順が変わっただけでは数え直さない） |
| 語彙 | 返答の `level`（`objective` / `job`）→ `MidGoalProposal.job`。`parse_proposal` は大目標の混ぜた条件と、手順の束の形を、設計や判定の前に確かめる。約束（promise）の経路は `level` を持たず、いつも大目標 |
| infrastructure | `JsonMissionStore`（`format: 2`、手順の欄、`next_step_id`、読めない形は `None` にして `.unreadable` に写す）、`stream_context`（手順を 済: / 今: / 待: と出どころで）、プロンプト（手順の見方、`kind` の決まり、返答の `level`） |
| presentation | `/api/goals` の中目標に `kind`・`steps`（`id` / `label` / `state` done・current・waiting / 出どころ / `progress`）・`steps_done`・`steps_total`。2 つのオーバーレイに今の大目標の手順、条件の数がなければ済んだ手順 / 手順の数のバー |

設計書から変えたこと・決めたこと:
- 視聴者の手順の位置は「今の手順のすぐ後ろ」だと、後から頼んだ人が先の人を追い越すので、「先に頼まれた手順の後ろ」にした
- `drop_step` はコードの操作だけ（Gemini の決定のスキーマには `drop` の手順版を足していない）。視聴者と助言の手順は、大目標が終わるか、済むか、予算切れか、本人の取り下げでなくなる
- 手順の判定は `MidGoalKeeper.judge`（小目標の切れ目ごと、決定の前）が持つ。`GoalChooser` は同じ結果を見て、満たした手順は済みにする（判定できなかったときの保険）
- 返答が手順を足したとき、`GenerateResponseResponse.mid_goal` は今の大目標（手順ではない）
- 保存の版は `format` の 1 つ。手順の `id` の欠けなど、細かい形の食い違いも `KeyError` などで読めない形になり、同じ道で始め直す
- 台本のコメント（§9 の 4 つ）と実機は未確認

## 13. 中目標と小目標の粒度をそろえる（2026-09-29）

ユーザー（2026-09-29）: 「中目標と小目標がほぼ同じ内容になってしまう。目標設定時の基準を見直してほしい」→ 案 A（プロンプト）と B（次の一歩）を両方進める。

原因: 中目標の書き方は「小目標の並び」と指示され（粒度の基準がなかった）、実際の中目標も `have(stick, 2)`、「小麦 2 個をパンにする」のような 1 回のクラフトや 1 種類の素材集めだった。通常の境目では Jev が中目標を選ぶだけなので、小目標は中目標と同じ条件になり、違いが生まれなかった。設計の意図（§1）は、中目標が仕事の単位、小目標が具体的な 1 回の遠征だった。

- **A. 基準（プロンプト）**: 中目標は成果物や状態の単位（石のツルハシを持つ、食料 8 個）で、1 回のクラフトや 1 種類の素材集めだけにしない（分解と次の一歩は自動）。悪い例（丸石 3 → 棒 2 → 石のツルハシの 3 つ）を示す。大目標・中目標・小目標の粒度を 1 文にそろえた（システム指示 `GOAL_SYSTEM_TEMPLATE` の「小目標の決め方」と jobs の節）。システム指示の長さの上限は 8000 → 8300
- **B. 小目標は中目標の次の一歩**: ブリッジの `/check` が、`have` の条件に `next_step`（have の条件）を返す（`solver.mjs` `nextStep`）。ソルバーの根の直接の子のうち、まだ足りず、集めに出るもの（掘る・狩る・チェストから出す。入手の方法 `node.method`）を含む最初のもの。クラフトと焼くのは自動なので、集めに出る材料を含まない子は飛ばす。持ち物がもう足りている子も飛ばす（同じ一歩の繰り返しを避ける）。例: 板材 16 枚 → 原木 4 個、石のツルハシ → 丸石 3 個（先に木のツルハシを作るのは自動）。集める物そのものが仕事なら一歩はなく、仕事が小目標のまま
- `GoalChooser` は、束でない `have` の中目標に `next_step` があれば、その一歩を小目標として Jev に見せる（理由は「中目標の理由（have(…) の一歩）」）。束（`together`）は分けない。一歩が終われば（小目標が済む）次の境目で同じ中目標からまた次の一歩を取り直し、集めに出るものが尽きたら中目標そのものが小目標（仕上げ）になる。中目標の済み・停滞・ラッチは今までどおり中目標の単位
- Gemini が小目標を決めるとき（失敗の後、見直し）にも、「中目標の今の状態」に `→ 次の一歩: have(…)` を添える
- オーバーレイの小目標の日本語 `label` は spec から作るので、一歩に変わればそのまま出る（中目標「石のツルハシ」の下に小目標「丸石を集める」）
- 限界（§14 で補う）: `have` の中目標だけ。`placed` / `built` / `farmed` などは今までどおり（中目標と小目標は同じ）。次の一歩は根の直接の子の 1 段だけ（深い分解は自動のまま）

## 14. 暗さと松明の在庫（2026-09-29）

ユーザー（2026-09-29）: 「また画面真っ暗です。一定の暗さで松明置くルールはどうなってますか？松明は常に一定数持つようにしたい」「暗すぎたら本来はなにも見えないので引き返して松明作るようにしてほしい」。

それまで: 暗さ（`isDark` = 頭の上がふさがっていて 8 ブロック以内に光源がない）で「今いる所に松明を置く」（`place_torch`）が出るのは松明を持っているときだけ。松明の在庫を保つ規則はなく、持っていなければ暗い所で何も見えないまま動き続けた。

- 集めるほうは既存の解決器のまま（木炭・採掘場の助言。§設計書 47 §16、CLAUDE.md の道具の消耗と木炭の項）
- 限界: 「暗い」の判定は `isDark`（洞窟の中など、光源が 8 ブロック以内にない所。判定は 2026-09-30 に直した、下）。松明を置く位置の間隔や、置いた松明の数の上限は変えていない

### 14.1 昼の木陰で暗いと判定しない（2026-09-30）

ユーザー（2026-09-30）: 「トーチの条件が昼間の木の下でも発動してしまっています。夜または半透明ブロックを除くブロックの下（地下や洞窟）で明るさが一定以下の場合にできますか」。確認して決めた: 夜は今のまま（夜の地上は暗いとせず、家に帰る側に任せる。`test/torch.test.mjs` の「夜の空の下: 地上は照らさない」）。

原因: `isCovered` は頭上 32 ブロックに `boundingBox === 'block'` があれば覆われているとし、除いたのは葉とガラスだけだった。木の幹・枝の原木、ハーフブロック、階段、柵まで覆いになり、木陰が昼でも「洞窟」と同じに扱われた。mineflayer の光の値は開けた地上で空の光 0 を返す（WORKLOG 2026-09-25）ので、明るさの閾値は光のデータでは作れない。

- **覆い**: `filterLight === 15`（光を通さない）のブロックだけ。葉・ガラス・氷など半透明は空の光を通す（葉の名前の一覧はやめた）
- **空の光の届き方**: 空の光は空が開いた柱から横へ 1 ブロックごとに 1 減る。モブが湧かないのは空の光が 8 以上（昼）なので、周囲（マンハッタン距離 7 以内）に空が開いた柱が 1 本でもあれば暗くない（`skyNear`、近い柱から見て最初に見つかれば終わる。読み込まれていない柱は数えない）
- `isDark` = 覆われている、かつ 7 ブロック以内に空が開いた柱がない、かつ 8 ブロック以内に光源がない。`isUnderground`（海面より下、覆われている）は新しい `isCovered` だけを使い、空の柱の確認は足していない
- 限界: 空の開いた柱かは「頭の高さから上」に不透明ブロックがないかで見る。自分より低い谷の底の空は開いていると数える。実機の木陰・洞窟での確認はまだ

## 16. 素材の採集だけの中目標を差し戻す（2026-09-29）

ユーザー（2026-09-29）: 「やっぱり中目標と小目標が同じになってしまっている」。

実測（`logs/goals`、`data/mission.json`）: 中目標が have(raw_iron, 3)・have(wheat, 6)・have(oak_log, 4)・have(planks, 6)・have(crafting_table, 1) で、Jev に出る選択肢も同じ、小目標もそのまま。§13 の次の一歩（B）は、作るものの中目標（have(stone_pickaxe, 1) → have(#stone_tool_materials, 3)）では効いていた。素材の採集そのものの中目標は、根の入手の方法が採集で次の一歩がなく、仕事がそのまま小目標になる。

原因は書く側だった: ①プロンプトの決まり（§13 A）を local モデルが守らなかった、②**決定のスキーマの説明が「jobs（小目標）… 1 つの外出ごとに 1 つ」「trips … 1 グループ = 1 つの中目標」と書いていて**（設計書 44 §9）、決まりと逆を指していた。決定の直前に読まれるスキーマの説明が勝っていた。

- スキーマの説明を直した: jobs は「持つもの・達する状態ごと（道具、食料の蓄え、建物の一部）で、外出ごとではない。素材の採集は次の一歩として自動で選ぶ。素材だけの中目標は差し戻される」、trips は「小目標は最初のグループに従う。中目標は外出ではない」。システム指示の該当の項にも 1 文
- コードで確かめる: ブリッジの `/check` が `gather`（have の条件の根の入手の方法が掘る・狩る・チェストから出す。まだ足りない）を返す（`solver.mjs` `isGather`）。`AdvancePlayUseCase._check_job_grain` は、書き直しの中目標に `gather` の単独の have があれば、大目標が要るものを添えて差し戻す。除く: 束（`together`。同じ外出でまとめて取る）、have 以外、大目標の完了条件そのもの、もう書いてある中目標。最後の試行は通す（差し戻し続けて決定が失敗するより、細かい中目標のほうがまし）
- 限界: 作るもの 1 回分（板材 4 など）は、材料を持っていれば次の一歩がなく小目標と同じになる（最後の一歩なので許す）。束の中目標は束のまま小目標になる。すでに保存されている素材だけの中目標は消えない（書き直しで落とす）

## 18. 大目標を決めたら LLM が計画を立てる（2026-09-30）

ユーザー（2026-09-30）: 「やはり今も中目標小目標が同じになっています」→ 調べると、§13 の次の一歩が効くのは束でない単独の `have` だけで（`GoalChooser` は `len(specs) == 1` のときだけ `next_step` を取り、ブリッジの `nextStep` は `have` の分岐にしかない）、`farmed` / `facility` / `placed` / 束の中目標はそのまま小目標になっていた。束は書く側でも中目標にされる（`_jobs_with_the_bundle`、`trips` の「小目標は最初のグループに従う」）。実測は、Jev が選んだ小目標 38 件のうち 18 件が中目標と同じ文。「大目標を決定したらソルバーに任せきらずに一度 LLM がプランを建てて小目標に並べてほしい。畑を広げる → 中目標 1. 土地の確保 2. 水源の確保 3. 土地を耕す 4. 種を蒔く、それぞれの小目標 2.1 バケツが必要なら作成 2.1.1 鉄がないなら確保 2.2 水を設置 …」。

## 19. 目標の照合と計画の検査（2026-09-30）

ユーザー（2026-09-30）: 「目標確認してると既に達成済みなのに管理画面ではチェックついてない（石のツルハシを持ってるのに）。自分の家を作る大目標の中に中目標として家の建築、家を建てるという目標がある。バリデータみたいなのって作れないですか」→ A（世界との照合）と B（計画の検査）の両方、終わった大目標の残りの中目標は閉じる、判定の負荷は許す。

### 原因（`data/mission.json` とコード）

1. 小目標の判定（`GoalChooser`）と中目標の判定（`ObjectiveKeeper._judge_steps`）は、**一番上の大目標のまだ済んでいない中目標**だけを世界に照らしていた。`ObjectivePlan.judge_steps` は済み以外の中目標を飛ばす。済んだ中目標の小目標、一番上でない大目標、終わった大目標の中目標は、一度も判定されなかった
2. 表示（`goal_board._steps`）は、判定していない小目標を `next_step({})` で「今」か「待ち」にしていた。石のツルハシの中目標 j17 は済みなのに、その小目標「石のツルハシを手に入れる」は「待ち」のまま
3. 終わった大目標「夜に寝られるようにする」は、中目標 3 つを未完了のまま抱えていた
4. LLM の計画を形で確かめていなかった。「自分の家を作る」（条件 `built`）の中目標に `built(house)` があった。`built(名前)` は設計した建物の名前で、`house` という建物はなく、ブリッジは「まだない」（`NotYetError`、未達）と答え続ける。つまり永遠に判定できず、小目標にもできない。同じ名前の中目標「石材の確保と工具作成」が 2 つ

### A. 世界との照合（`ObjectiveKeeper._reconcile`）

- `judge`（小目標の切れ目ごと）の最後に、**すべての未完了の大目標の、すべての中目標（済みも）の条件と計画の小目標**を `/check` 1 回で判定し、今満たしている条件の名前を `Job.met_now` に残す（`ObjectivePlan.reconcile`）。済み（ラッチ、設計書 50 §4）は変えない: 材料を使って崩れても済みのまま
- 1 つでも拒否されたら（400 は 1 回分すべてが拒否される）半分ずつに分けて判定し直し、拒否された条件だけ「満たしていない」扱いにする。ブリッジにつながらなければ前の照合のまま
- `met_now` は保存しない（古い真偽が再起動後に残らない）。表示だけが使い、ソルバーや小目標の選択は使わない
- 表示（`goal_board._jobs` / `_steps`、管理画面の目標ツリー、オーバーレイ）: 小目標は **done**（一度満たした、または中目標が済んだ: 中目標の状態を達したなら小目標は要らない）/ **met**（いま満たしている）/ **current**（今の大目標の今の中目標の、満たしていない前提のいちばん奥）/ waiting / **closed**。中目標は done / met / current / waiting / closed。「今」が付くのは一番上の大目標だけ（前は大目標ごとに付いた）。`jobs_done` は met も数え、`jobs_total` は closed を数えない
- 大目標が終わったら（済み・断念）、まだ済んでいない中目標を `JobState.CLOSED` にする（`Objective.closed()`、`ObjectivePlan._finish`）。保存済みで閉じていないもの（この日の `夜に寝られるようにする`）は `ObjectivePlan.finished` が閉じて見せる

### B. 計画の検査（`use_cases/plan_lint.py` `check_plan`）

計画を書くとき（`JobPlanner.plan`、`_check_bridge` の後）と、目標の決定が中目標を書き直すとき（`_decide_goal`、`_check_job_grain` と同じく最後の試行は通す）に、形で確かめて理由つきで書き直させる。

- 存在しない名前の `built(名前)`（中目標、束、計画の小目標）。通るのは、その大目標の完了条件に入っている名前と `GET /builds` にある名前。家そのものは名前なしの `built`
- 大目標の完了条件そのものの中目標が、最後でない
- 同じ条件の中目標、同じ title で条件の違う中目標、済んだ中目標と同じ title で条件の違う中目標（済んだものと同じ条件を書き直しに書いてきたのは、今までどおり足されずに残る）
- プロンプト（`PLAN_TEMPLATE`）に同じ決まりを 2 行足した

**入れなかったもの**: (1) 「大目標の条件と同じ中目標」を全部断ること — 計画の決まり（最後の中目標は大目標の完了条件に達する）と、`unplanned`（中目標が尽きたら計画を書き直す）に反し、書き直しが止まらなくなる。最後の 1 つだけ許す。(2) 別の大目標の完了条件と同じ中目標を断ること — 一番上の大目標が計画を書くときは、それより上の大目標は済んでいるので起きない。下の大目標の成果物を先にやるのは正当な並べ替え。(3) 書いた時点で満たしている小目標を断ること — 前提は満たしていれば飛ばす決まりで、表示（A）の問題だった。

### 書いてあった判定できない中目標の片付け（`_drop_unjudgeable`）

`plan_lint` は新しい計画しか止めないので、すでに書いてあった `built(house)` の中目標は、小目標として出されては拒否され続ける。`judge` のたびに、存在しない名前の建物が条件の中目標（視聴者の頼み・助言のものは除く）を外す。外して中目標が尽きた大目標は、次の切れ目で `unplanned` により計画を書き直す（検査つき）。小目標だけが存在しない建物を指す場合は外さない（中目標ごと捨てると材料の段階を失う。計画の書き直しに任せる）。

### 限界

- `met_now` は判定の負荷が 1 回分増える（重複を除いた全条件を 1 回、拒否があれば分割して数回）。小目標の切れ目ごと
- 照合するのは未完了の大目標だけ。終わった大目標の小目標は、最後に照合したときの `met_now` のまま（閉じた中目標に付く）
- 実機で、今の `mission.json` のコピーを本物のブリッジに照合させて確かめた: 石のツルハシの小目標は済み、`built(house)` の中目標は外れ、終わった大目標の中目標は閉じた
